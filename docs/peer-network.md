# Peer network

How two ELU installs find each other, what they send, and how a team keeps its list of
members. This page is also the A2A custom binding document (A2A v1.0.1 §12 requires one for a
custom binding). The commands a person types are in [Teammates](teammates.md).

## What it does

1. Your agents talk to your teammates' agents, machine to machine, with no company server.
   - **ask:** a message to a teammate. It always reaches them; what it does on their machine is their setting for the team (see [What teammates can do here](#what-teammates-can-do-here)).
   - **ask a bot:** a question to one teammate can name a bot they share. That bot answers it in place of their model.
   - **review:** a diff sent for a read-only review.
   - **pictures:** a message you type to a teammate or a channel takes along the pictures it names. See [Pictures](#pictures).
   - **handoff:** a goal for their machine, handled like any other message.
   - **status and overlap:** teammates see each other's live agents and get a warning when two agents edit the same file.
   - Agents can draft asks themselves. A draft is sent only when you approve it, or automatically to teammates you set to auto.
2. A2A v1.0 data model end to end. A local A2A JSON-RPC endpoint on 127.0.0.1, off by default, lets other A2A tools reach your agent and, through it, your teammates.
3. Sessions shows peer items that need you. **Chats** shows channels, teammates, their agents and threads.

Not supported:

- One device per person; no multi-device.
- Offline catch-up only through the sender's outbox, with no always-on mirror.
- Handoffs are text goals, not patches.
- Only pictures travel with a message to a teammate (PNG, JPEG, GIF, WebP). Other files go only to a session of a shared project on another computer (see [Files](#files)).
- No Windows support.
- A share grants the whole repository (tracked files minus sensitive ones), not per-path globs.

## Layers

```
identity    ed25519 key per install (Node crypto), shown as hex + 8-char fingerprint
roster      per team: signed append-only log of create/admit/remove/role/relays/leave/channel ops
discovery   each daemon announces its own key on HyperDHT; teammates are dialled by key
transport   Hyperswarm (Noise IK, UDP holepunch) -> a teammate's computer passing it along -> blind relay you run -> outbox retry
binding     newline-delimited JSON-RPC 2.0 over the Noise stream (this document)
messages    A2A v1.0 Message/Task/Artifact + extension urn:elu-code:a2a-ext:peer:v1
channels    team: pairwise A2A tasks + status notifications
conductor   peer daemon <-> conductor through files only (requests, outbox, commands)
```

There is no ELU server anywhere, and nothing to turn on. The daemon runs while this machine is an active member of at least one team, or has left one without any teammate hearing it yet:

- Nothing starts on a machine that never made or joined a team, and it makes no peer connection.
- `/invite`, `elu team create` and `elu invite` start it once the team exists; `/join` and `elu join` start it for the join, through a `join` command it reads when it starts. While the join looks for the inviter the app and the shell count the seconds; Esc or Ctrl-C takes the `join` back if no daemon has read it and sends `joinCancel`, which ends the search at once, with a short code or a long one. Quitting the app does the same before it closes. The `join` names the process that asked (`pid`), and the daemon ends a join whose asker is gone, so a join never goes through with nobody there. A cancel that arrives while the proof is with the inviter waits for the answer: admitted, the join stands on both computers; refused or unanswered, it ends as cancelled. No member is left at the inviter's that is on no team at the joiner's. A search that finds nobody in 60 seconds answers why and what to do; one on a machine whose DHT got no answer at all, or went offline, answers that as soon as the first lookup is over. The app starts it when it opens on a machine on a team, and again within a minute when it stops. It is a detached process, so it keeps running when the app closes.
- `/leave` and `elu team leave` take this machine off a team. Leaving the last one once a teammate has the leave, or hearing that an admin removed this machine from it (`/remove`, `elu team remove`), stops the daemon at once. A leave no teammate has heard keeps it running until one has (see [Leaving and removing](#roster)), and the app starts it for that as it opens. Otherwise, with no team, no join and no command under way for 60 seconds (a join that failed, say), it stops by itself. `peer --daemon` started with no team, no unheard leave and no command waiting, by a login service say, exits before it connects.
- A daemon of another version left running on a machine on no team (0.1.5 started one before a join, which may have failed) is stopped when the app opens, and by `elu peers` and the `elu` commands that need a team.
- `elu peer off`, `elu peer uninstall` and `elu uninstall` stop it, but only until the app opens or an `elu` peer command runs while the machine is still on a team.
- An `enabled` field in `settings.json`, written by 0.1.5 and earlier, is ignored.

Defaults that touch third parties:

- the HyperDHT bootstrap nodes. HyperDHT's own public nodes are used unless `bootstrap` in `peer/settings.json` names others; the routing table is cached after the first join.
- other HyperDHT nodes. Announcing the key and dialling a teammate send requests to DHT nodes that anyone may run, and they see this machine's IP address and port.
  - The daemon's own DHT node is ephemeral: it is never added to other nodes' routing tables, so strangers' lookups, announcements and connections are not routed through it, however long it runs.
  - A relay you run keeps HyperDHT's default instead: on a reachable server it can join other nodes' routing tables after about 20 minutes and route lookups for anyone.
  - While an invite is open and a teammate's computer can pass the join along, a small sealed record is stored on DHT nodes. Only someone with the code can read it (see [When two computers cannot connect](#when-two-computers-cannot-connect)).

## Binding: `urn:elu-code:a2a-binding:hyperswarm-ndjson:v1`

- **Transport.** A Hyperswarm connection. Noise IK authenticates both device keys. Each side `listen()`s on its own key pair, and a teammate is dialled with `swarm.joinPeer(key)`.
- **Framing.** One UTF-8 JSON object per line; a frame may be at most 1 MiB. A larger frame closes the connection.
- **JSON-RPC 2.0, both directions.** Either side may send requests; responses are matched by `id`. Notifications have no `id`. Requests time out after 30 s.
- **First frame.** Each side's first frame must be `elu.hello` with params `{binding, a2aVersion: "1.0", name, teams: [{id, seq, head, ops}], handles, plans}`. `plans: true` says this build reads [Tasks](#tasks), and `lists: 1` that it joins a list of Tasks or cards sent in parts; a build that does not know a field ignores it. With no valid hello within 5 s, the connection closes.
  - The hello is written for the receiver's key, which Noise has proved before the first frame. `teams` lists only the sender's teams that this key is an active member of in the sender's log. `name` is the sender's display name when `teams` lists one, and empty otherwise.
  - `ops` (at most 8 per team) are the roster ops that admit the sender, so a teammate admitted elsewhere can prove it. They are merged only for a key the receiver has never seen in that team.
  - `handles` (at most 20) are the sender's share handles that the receiver may ask about: the projects shared with a team both machines are on. A teammate admitted by this same exchange gets them on the next connect.
  - **Service parameters.** A2A-Version travels as `a2aVersion`; any `1.x` is accepted, and another major version closes the connection with a logged reason. The only extension, `urn:elu-code:a2a-ext:peer:v1`, is listed in each `Message.extensions` (A2A-Extensions has no other carrier here).
- **Admission.** The Hyperswarm firewall admits every key. The application layer then accepts a connection only if:
  - the remote key is an active member of a team we share; or
  - its hello carries roster ops that validly extend our log and make it a member; or
  - an invite of this machine is still open, and the connection uses it: `elu.invite.start` then `elu.invite.prove` for a short code, or `elu.join` for a long code from 0.1.3 or earlier (see [Invites](#roster)). Nothing else may be sent first.

  Anything else is closed. The decision is logged.

  Before admission, a key on none of this machine's teams (a stranger, someone removed from them, a joiner) is sent only the hello `{binding, a2aVersion, name: "", teams: [], handles: [], plans: true}`: no team, no member and no name. A joiner gets the roster in the reply to `elu.invite.prove` (or `elu.join`). On a direct connection the handshake also shows the other side this machine's IP address and port.
- **Methods.**
  - **A2A core:** `SendMessage`, `GetTask`, `CancelTask`. The push-config methods return PushNotificationNotSupported; any other core method returns UnsupportedOperation.
  - `SendMessage` never blocks: it returns the Task (SUBMITTED, or REJECTED with a reason) at once, whatever `returnImmediately` says. Later states arrive as `elu.taskUpdate` or through `GetTask`.
  - Unknown fields in A2A objects and params are ignored (A2A §5.7); size limits still apply.
  - **Extensions:** `elu.hello`, `elu.invite.start` `{topic, nonce}`, `elu.invite.prove` `{proof, name, exits?}`, `elu.join` `{teamId, secret, name}`, `elu.roster.get` `{teamId, after}`, `elu.roster.push` `{teamId, ops}`, `elu.picture.put` `{id, seq, last, size, sha256, data}` (see [Pictures](#pictures)), `elu.text.put` with the same fields (see [Long messages](#long-messages)), `elu.list.put` `{list, id, seq, last, rows}` (see [Tasks](#tasks), "Size"), `elu.carry` `{with}` (see [When two computers cannot connect](#when-two-computers-cannot-connect)), and the `elu.remote.*` methods between computers on a shared project, `elu.remote.files` among them (see [Computers on a shared project](#computers-on-a-shared-project)). `elu.mine` and `elu.own` from ELU 0.1.26 to 0.1.33 are taken silently and never sent.
  - **Notifications:** `elu.status` `{rows, box, bots: [{name, about}]}`, `elu.plans` `{tasks}`, `elu.route` `{relays}` and `elu.taskUpdate` `{task}`. `box` and `bots` are described under [Status](#status), `elu.plans` under [Tasks](#tasks).
- **Errors.** JSON-RPC error objects; `data` is a list of `google.rpc.ErrorInfo` with `reason` set to the code's name. Messages carry no local paths, unless the caller is a peer I trust (`trusted` in `peers.json`), who gets them as written.

  | code | meaning | the asker |
  |---|---|---|
  | -32000 | too many requests (more than 20 in 10 s; more than 40 closes the connection), or a file here is locked by another ELU command for a moment | retries with backoff |
  | -32001 | TaskNotFound | marks the ask failed |
  | -32002 | TaskNotCancelable | stops cancelling |
  | -32003 | PushNotificationNotSupported | |
  | -32004 | UnsupportedOperation | marks the ask failed |
  | -32009 | VersionNotSupported | |
  | -32602 | invalid params, including every refusal | marks the ask failed |
  | -32603 | internal error | retries with backoff |

- **Idempotency.** `SendMessage` is idempotent on (sender key, `messageId`). A repeat returns the original Task. The sender stores the server's `taskId` in `asks/` and polls `GetTask` when it reconnects.
- **Exact names.** JSON field names, enum strings and method names must match A2A v1.0.1 (`specification/a2a.proto` and `docs/specification.md` at tag v1.0.1). `lib/peer/a2a.mjs` cites the section each one comes from.

Extension `urn:elu-code:a2a-ext:peer:v1`:

- It is listed in `Message.extensions`.
- Its data lives in `metadata["urn:elu-code:a2a-ext:peer:v1"]` = `{kind, project, hop, from: {key, name}, team?, room?, bot?}`. `team: true` marks a team ask; older peers drop it and show a plain ask.
- `kind` is one of `ask`, `review`, `handoff`, `answer`, `result`.
- `result` is the outcome of work the receiver's owner approved after a message of the sender's started his session (below). It goes in the thread (`contextId`) that message started and runs nothing: the receiver takes it only from the teammate a message of its own in that thread went to, still on a team with it, writes it to the thread as `{dir: "in", kind: "result"}`, keeps it on that ask as `result` (the thread's row shows it), continues the chat that message came from with it as peer data when `autoContinue` is on for that teammate (as an answer does), and answers with a COMPLETED task. An answer or a result a chat went on with stays listed in its thread for a week (`continued: true` on the item), and is no row in Sessions. The same `messageId` again is kept once. A result has no length limit of ELU's: one too long for a line on the link goes in pieces first, as any message does (see [Long messages](#long-messages)). An older receiver refuses it as invalid params, and the sender drops it.
- `project` is a share handle or repository id, or null for the team's project.
  - The receiver takes a named project only when it shared it with a team both machines are on. A project shared with another team is refused in the same words as one that is not shared.
  - With null, the receiver uses the project of its [setting](#what-teammates-can-do-here) for the team, else the share chosen for the team, else its one share. Without any, the message is still taken (SUBMITTED) and waits for the owner, who approves it in a project he has open. ELU 0.1.6 and earlier refuse it instead, with "They have not shared a project, so there is nothing of theirs to ask about yet."; a newer sender shows that refusal as a line saying the teammate needs to update.
  - A share saved by a build from before shares kept their teams is open to every team of the receiver's until it is shared again.
- `room: {team, channel}` says where a team ask was sent. `team` is the team id. `channel` is the channel id, or null for `#general`.
  - The receiver keeps the room only when both machines are on that team and, for a channel, both are in it. Otherwise it drops the room and shows a team ask with no channel.
  - A room whose ids are malformed is refused as invalid params.
  - Older peers drop the field.
- `bot` names one of the receiver's shared bots, the one the question is for.
  - It is a bot name: 1 to 30 lowercase letters, digits or `-`, starting with a letter. Anything else is refused as invalid params.
  - Only an `ask` to one teammate may carry it. With another kind, or with `team: true`, the message is refused as invalid params.
  - Older peers drop the field. There the question reaches the person as a plain ask.

## What teammates can do here

Each machine keeps one setting per team in `peer/access.json` = `{teamId: {handling, rules, root, at, home?}}`. It is never sent; nothing on the wire changed for it.

- `handling` is `auto` or `manual`. The teams that decide a message are the teams of the project it runs in: those the project is shared with that both machines are on (every common team for a share without teams), plus the common teams whose `root` is that project. The sender's `room` never chooses among them. When every one of them is `auto` with that project as its `root`, an incoming `ask`, `review` or `handoff` (not one for a shared bot, and not a team ask) is queued at once as the owner's own kind of session: a request with `origin.kind` `handoff`, `origin.own: true`, `origin.teams` those teams, the owner's default permission mode (`full` too: it runs as if the owner had typed it), place `worktree` and no extra folders. A later message in the thread continues the session in its current mode, `full` included. Its Task is approved as one he typed would be: in `auto` and `full` the mode approves it and the work goes on in the same request; in `ask` it waits for his approval, and the reply says so. Once he approves it, the conductor writes `outbox/result-<requestId>.json` when that Task is finished, whichever turn of his finishes it (a run that stops on a question sends nothing yet; a turn that does the Task's work and fails or is stopped says so, once for a Task however often its work stops). It counts the same however he approved: with the key, or by typing yes; and a later message of his that carries the work on counts as the run that started it. A run the conductor queues again after a stall or a rate limit says nothing: it starts the same approved work again, and so does r on it. The daemon sends what the work did into the sender's thread as a `result` message. It is sent once for a Task, with the same secret scan as an ask. When the owner holds his replies to that teammate, or the text may carry a secret, it is not sent: it waits with his held replies (`held:result-<id>`), where y sends it, an edited text replaces it and is scanned again (e on it, in Chats or in Sessions, opens its text in the message box), and n drops it. `holdReplies` and `autoContinue` are the owner's own flags for a teammate in `peers.json`, never sent; h and o on the teammate in Chats set them (the daemon command `peerSetting`). Otherwise it waits (SUBMITTED) until the owner's y, which queues the same request in his default mode, marked `typed`: what he accepts with his own key (y or w, in Chats or on its card) is his decision at that moment, so it starts at once, as anything he types does. A team with no entry is `manual` with no rules.
- These sessions count toward `peerSlots`. One that starts by itself (Auto, or `autoAccept`) waits for a free one, and past the number `/slots` sets for a free slot as well; one the owner accepted with his key waits for neither. A session started as the owner's own runs as one he typed: ELU caps none of its turns, and its work takes what he sends while it runs, answers his questions beside a turn, is carried on in Approve for me and Full access, and answers a standup. What it costs is the owner's: none of it is charged to the teammate's thread, daily or team allowance, and what intake reserved for the message is given back when he takes it (the record keeps `own: true`; one without it is charged as before). Nor is it one of the teammate's requests: it counts toward neither `threadMessages` nor `peerRunsPerDay`, and the request a message counted while it waited for him is given back when he takes it with y or w. A message Auto takes as his own is checked against `hops` and the 200 messages a day only, and reserves nothing. A teammate's question is charged what it cost when its reply goes out; an outbox entry with no cost (`costUsd: null`) is charged the whole reservation. Each turn of a teammate's question is capped at `caps.runUsd`.
- `rules` is the owner's plain-English text, of any length. Every turn of a session a teammate started (`task.origin.peer` set) is told it under "The owner's rules for teammates", read when the turn starts. It gets the rules of every team in `origin.teams`; a session without them gets the rules of every team the teammate is on. So is every turn that answers what another computer on a shared project sent (a request with `computer`, or `adds` for words it typed into a run that waited here), in whoever's session: the one it starts, the turn it joins while that works ("... wrote to this session from another computer on this project ..."), the answer beside a turn, and the turns of a Task it approved. Such a message is never joined to the owner's own into one turn, and his next message is told no rules.
- `root` is the project those sessions run in: the folder `/join` (or `elu join`) ran in, the one `/invite` shared, the project open in `/access`, or the project `elu access` changed it in, from any folder in it (`--project PATH` names another). It is used when it is a registered project, and is never the home folder or above it.
- `home` is `true` only where the owner allowed the home folder itself as this team's project: y to "This project is your home folder. Let the other computers on it work here without asking?", which `/access` asks when he picks Auto there, or `elu access --auto --home` run there. `root` stays `null`, as it always was for the home folder, so an ELU up to 0.1.34 reads the row as before and keeps that work by hand; a row it saves has no `home`. It is kept only while `handling` is `auto` and no project is saved: Manual, or a project saved with `root`, drops it. It decides only what another computer on the project asks (`elu.remote.*`, below); a teammate's message of Chats still asks for the home folder each time (next point).
- A session a teammate's message starts (`task.origin.peer` set) never works in the home folder or a folder above it, and never edits a repository there, unless the owner allowed it. Where the session works decides (its `worktree`): one whose project is the home folder but that edits in a repository's own folder is not there. The owner at the keyboard (typing, replying, approving, retrying) is asked "This session's project is your home folder. Let it run here?"; y keeps `homeAllowed: true` on the session (or `home: true` on the request that starts one) and the message goes at once, and n sends nothing. `elu allow-home <session>` does the same from the command line. An unattended message (Auto) never runs there: intake picks no such root, and a request that reaches the conductor for such a session waits under Needs you with the same question. The conductor and the session refuse anything else, whatever path reaches them.
- The teammate's own text is kept on the session's message as `context` (and `words`, apart from the note on any pictures). The chat, the session's details, `elu status`, the follow-up box and the lists show it under their name; the sentence written for the model stays in its prompt. Retry never sends a teammate's message again as the owner's.
- Asked by `/join` before the join, by the first `/invite` for a team before its code, and changed with `/access` or `elu access [--auto|--manual] [--rules TEXT] [--project PATH] [--home]`. `elu join` and `elu invite` take `--auto`, `--manual` and `--rules` too. Without either, `elu invite` on a team that already has other members saves `manual`.
- Leaving a team (`teamLeave`, or the leave written here when the daemon cannot start) and coming back to it with a new invite drop its entry along with its shares. Hearing that this machine was removed from it drops its entry only; its shares are dropped when it comes back. Joining again sets the entry again: `/join` asks, and `elu join` saves its flags or the defaults (`auto`, no rules).
- A question for a shared bot (`bot` in the extension) waits for the owner as before, and is refused when the receiver has no project for it. A teammate set to `autoAccept` in `peers.json` still has its asks and reviews answered read-only while the team has no setting.

Task state mapping:

| ELU | A2A |
|---|---|
| waiting for the owner to approve | SUBMITTED |
| run in progress | WORKING, with ext metadata `{session: "<its name>"}` once it has a session that Sessions lists there |
| reply held for the owner's approval | WORKING, with ext metadata `{substate: "awaiting-owner"}` |
| reply sent | COMPLETED, with the reply as one Artifact (text part) |
| owner declined, or blocked by policy or caps | REJECTED, with a reason message |
| run failed or was stopped | FAILED, with a reason message |
| asker cancelled | CANCELED |

A FAILED task says why, and the one thing to do (`lib/peer/failure.mjs`): the stop line the answering machine shows its own user, put for a reader who is not at it. It names that machine (`@name` as the team calls its owner, the same for every computer), as in "Grok Build is signed out. Sign Grok Build in on @kai, then send it again." A teammate's computer gets it with paths cut and no account named, a trusted teammate's with paths kept, and a reason that may hold a secret stays on the answering machine. It is at most 300 characters. A SUBMITTED task may carry a message too: a machine with no project for teammates' messages says so, and what to do there, while the message waits for its owner; and a message written to that machine alone (not to a channel) that waits for its owner's yes, as on a machine set to Manual, says so: a teammate reads "It waits for its owner on @kai, who approves each message from a teammate. On @kai: y on the message starts it, and /access set to Auto starts the next ones without asking." (a question for a shared bot names the bot) The sender shows both under its message in Chats and in the opened thread. A machine on 0.1.19 or earlier sends only "The run failed.", which the sender shows as "The run failed on @name. Update ELU there to see why."

The sender follows its message (`sentState` in `lib/terminal-visuals.mjs`), in the line under the chat after it is sent (read again every two seconds while it is still the line shown), in the reply row of its thread, and in the thread itself while it is open (read again every two seconds too):

- **Not connected yet.** The message is kept in `peer/asks/<id>.json` (`pending`) and goes by itself when that computer connects. The line says that first when the roster shows it offline: "@name is offline (1m). Your message goes as soon as it connects.", with how long it has waited.
- **Delivered.** The first Task that comes back sets `deliveredAt`: "Delivered to @name at 20:14.", with what the message waits for there when that computer says it. That it waits is never said with no reason.
- **Started there.** A WORKING Task whose ext metadata names the session (`session`, the name its row in Sessions has on that computer) is kept as `startedAs`: 'Started on @name as session "<name>".' A teammate's question, which is answered in its thread there and not listed as a session, names none and reads "@name is working on it."
- **Answered, or failed there.** "@name answered. The reply is in Chats." or "Failed on @name: <the reason and the one thing to do>".

The answering machine keeps the same failure in its own words (`failure` on the record: the stop line of the session there, as its row in Sessions and the session itself show it). Its thread in Chats shows it under the message ("your model could not answer · <reason>"), the line under its chat says once that a message from @name failed there and why, and `elu peers` prints it whole: `failed  @name  <message> · <reason>`, on the sender's side with the reason that came back. Where two computers on a team go by the same person's name, `@name` is each one's computer name.

## Computers on a shared project

There is no "mine": ELU removed it after 0.1.33. An invite shares a project, and every computer on that project sees its sessions on each of the others and works on them under that project's access rules on the computer that runs them, the same way whoever owns it, the owner's own other computers included. A computer that shares no project with this one is refused everything below, and nothing of a project that was never shared, or is kept off with `/share off`, is listed, watched or sent.

- **What became of mine.** A computer marks no other. `/mine` and `elu mine` answer one line, "Every computer on a project works the same: there is nothing to mark.", and `/mine` is no longer listed. `peer/mine.json`, which ELU 0.1.26 to 0.1.33 wrote, is left on disk as it is, and no power or label is read from it: only the one-time repair of what ELU 0.1.29 mixed (below) still looks at the old marks. `peer/github.json` is left too, and read by nothing. Since ELU 0.1.49 the owner's computers pair through his GitHub account again, one-sided (`peer/github-pairing.json`, [the Orchestrator](orchestrator.md#your-computers)): that pairing says only which computers are his, for the Orchestrator, and changes no project's access rules. There is no `elu invite --mine` or `elu join --mine`, and no row says a computer "says it is yours". An invite made by ELU up to 0.1.33 for another computer of its owner's joins as an ordinary invite: its `mineOffer` is not asked about.
- **Older computers.** `elu.mine` and `elu.own` from ELU 0.1.26 to 0.1.33 are taken silently: nothing is marked, said or granted, and neither is ever sent. Such a computer goes on sending its requests as before; each is handled as one from any computer on the project (below). What it reads back stays as it was: `elu.remote.list` keeps `mineByPeer: true`, and a session it started lists with its `remoteId`.
- `hello` carries `remote: 1`. A build without it is older: it is never sent the methods below, and every action toward it says "@name needs to update ELU to run sessions from here." Nothing falls back to an ask.
- `hello` carries `files: 1` on a build that takes files (`elu.remote.files`). Files are never sent to a computer whose hello says `remote: 1` without it, nor to one that answers Method not found: the owner is told "@name needs to update ELU to receive files."
- `hello` carries `startFiles: 1` on a build that takes files with the message that starts a session (ELU 0.1.30 and later). To a computer whose hello says `remote: 1` without it, none are sent: the owner is asked "@name has an older ELU, which takes files only into a session that has started. Start it with the text only?", and n or Esc keeps the message in the box. The same question says "@name is offline, and files cannot wait for it." while it is offline.
- `hello` carries `folders: 1` on a build that lets the owner pick the folder a session works in (`elu.remote.folders`). A computer whose hello says `remote: 1` without it is never asked, and its sessions start where they did.
- **What the app calls one.** Each computer is listed by its name, with its person where known: `@devbox · ana` in Chats, "On devbox · ana" over its sessions. Every computer the same way; its name on the team still reaches it when typed. A message written to it as `@name text` is an ask like any member's: the team's Auto or Manual setting, its rules and the daily limits apply.

- Every request and notification above is refused with "Only computers on a project with this one can do this." unless the sender shares a team with this computer, and names only the sessions and projects of a project shared with that team that the sender has a folder of (any other is "That project is not on this computer." or "That session is not on this computer."). Reading (`list`, `watch`, `since`, `older`, `folders`, `board`, and `check` with `look`) needs nothing more. Acting (`start`, `send`, `files`, `answer`, `task`, `rename`, `archive`, `delete`, `check` with an answer, `boardAct`, and a standup's question) goes by that project's access here (`/access`, `elu access`): with every team of the project set to Auto for it, it is done at once. Otherwise (Manual, a team with no setting, teams that disagree, or the home folder until its owner allowed it with `home`, above) a new session or a message waits for the owner's yes here (`r` on it in Sessions; the answer to `start` and `send` says `waits: true`, and the sender's status line says "It waits for a yes there."), and the rest is refused with "This project takes its work by hand. Do it there, or set /access to Auto there." (for a folder above the home folder, which is never Auto, "Its project holds its whole home folder, where work is always by hand. Do it there."), which the computer that asked shows after this computer's name. A message typed into a new session that still waits for that yes is refused with "It has not started: it waits for a yes there. Write to it once it has." Stopping a session that computer started stays its own. An `id` (a UUID the viewer chose) belongs to the key that started it; to any other key it is "That session is not on this computer."
- `start` runs the message as a new session in a project shared with that computer: the one a team both are on set with `/access`, else the only one, else the one the viewer picks (`folders`). With none it is refused with "No project here is shared with that computer." `permissions` is `ask`, `auto` or `full`, kept within this computer's own default mode (a higher one is lowered to it); `place` and `model` are as for a local session, and `bots` are names of the host's own bots (one it lacks is refused). The never list, the sandbox and the host's limits apply; the owner's saved rules (`a`, `/permissions rules`) do not: the session answers to the defaults and that team's `/access` rules, as a teammate's does. It starts by itself, so it waits for a free slot once the number `/slots` sets here is reached, and takes none of the teammate slots (`peerSlots`); one the owner here says yes to starts at once. The answer names the project by its folder's name here (`project`) and by its id as `list` names it (`projectId`), so the viewer says it by the name the project has there. The request names that computer (`computer`, its key); the task's `origin` is `{kind: "mine", mine: true, machine, name, remoteId}`, a record name kept as ELU up to 0.1.33 wrote it.
- `folders` says where a `start` would run (`root`, the project's folder there, and `project`, its name), and `pick` is true while several projects there are shared with that computer and no team setting decides. Then `folders` lists those projects alone (`label` is its path from the home folder, `~/shop`), never another folder there. The viewer's app asks before the session starts: "Folder on @devbox", one row each, the cursor on `root`; Enter starts it with that `folder`, and Esc sends nothing and keeps the message in the box. A `folder` that is not one of them is refused with "Pick one of the folders listed." and nothing is queued.
- Events are numbered per session from 1 and kept on the host (the newest 4000) in `peer/remote/host/<id>.jsonl`. Each is `{seq, at, type, ...}`, with `type` one of `state` (`state, title, mode, place, bots, activeRole, error, question, choices, since?`; `since` as in the list below, sent while a turn works and for a session that has not started yet), `entry` (a chat message: `n, role, at, text, lead?, bot?, failed?, quiet?, shell?, computer?`; `computer`, on a message of the owner's kind, is the key of the computer it was typed on: the one that sent it, else the host. Each computer reads a message typed on itself as You and any other as that computer's person on it (`ana on @devbox`), the host's own chat too; one from an older host says none and reads You, as before; `n` is its place in the chat, from 1; a bot's review saved by ELU 0.1.19 or earlier has no time of its own and goes with the end of that bot's run, or with `at: null` when that run is not known; the viewer draws an entry with no time after the entry before it, never above the first message), `step` (`at, text`), `approvals` (`list: [{id, role, summary, at, always?}]`, all that wait now; `always` is the rule `a` would keep, in words, only where the host offers `a`), `plan` (the shared Task, or null) and `diff` (`summary, patch`). An entry and a diff are sent whole, whatever their length: one event carries up to 60,000 characters of the text, with `more: true` when there is more, and the rest follows in order in `entry+` events (`text, more?`) or `diff+` events (`patch, more?`). The viewer shows the entry or the diff once its last event is in. An older viewer ignores those events and shows the first 16,000 characters of such an entry. The diff is what the host's own Changes view shows; while the session works it is read again every 10 seconds, and a long one less often. A notification holds up to 400 KB of events (at least one); when a session has more, its `last` is past what was sent and the viewer asks for the rest with `elu.remote.since`, whose answer has the same size.
- The first look sends a session's newest 80 entries, and the viewer keeps the newest 200 as they arrive. Neither is the end of the chat. The `n` of the oldest entry the viewer holds says how many come before it; the chat shows that count on a line over it, and when the owner pages up to that line the viewer asks `elu.remote.older` with `{id, from, before}`: the entries at the places `from` up to `before` (80 at a time). The host sends them as `entry` events at its next look, whether or not they went out once, and starts every later look at `from`. The viewer puts them in time order, keeps one it already holds once, and lets none go from then on. The line reads `Loading earlier messages from @devbox…` until they are in, and is gone at the first entry. A host on ELU 0.1.19 or earlier sends no `n` and does not know `elu.remote.older`: the viewer shows what it was sent, with no line. A session followed since then holds entries with no `n`: paged to the top, the viewer asks `elu.remote.older` with `{id, places: true}`, and the host sends the entries of its look again, each with its `n`.
- The viewer shows every line of the diff in the session's Changes view (`d` on its row or in its pane, then Enter, or `/changes`), the same view a session of this computer has. The name of that view's tab counts the files (`Chat   Changes 7`), and the chat holds no line for them, as the chat of a session of this computer holds none.
- `error`, in a `state` event and on a row of the list, is the stop line of a session that waits for its owner, put for a reader who is not at the host (`lib/peer/failure.mjs`): why it stopped, and the one thing to do, naming the host by its machine name, as in "Grok Build is signed out. Sign Grok Build in on @devbox, then send it again." Paths are cut and no account is named, as for any teammate.
- The viewer folds them, in order, into `peer/remote/view/<id>.json`. On a gap, and on each new connection, it asks `elu.remote.since` from its last `seq`, a few sessions at a time. When `first` is past its `seq`, the older events are gone and it continues from `first`.
- A `state` event also says what waits there, and leaves both fields out when nothing does. `held` is how many of the owner's messages wait for the turn that works; the viewer offers to send them now. `waits` is what the next message waits for before its turn starts, while the session does not work: `{on: "slot", running, limit}` (no free slot: `/slots` on the host changes `limit`; a host with no limit set, as every host is until `/slots` sets one, never sends it), `{on: "teammates", running, limit}` (no free slot for teammates' work) or `{on: "time", until, why?}` (it tries again then). The viewer checks each field and says it in the sentence the host's own chat shows, and lists a `starting` session that waits as a queued one.
- What the owner types on the host always starts; the number `/slots` sets limits what starts by itself. What another computer asks for there (a new session, a message, files, an approved Task) never counts as typed on the host, whoever owns that computer, and whatever `typed` it sends: it starts by itself, so the number `/slots` sets holds it back, as it does a schedule's run, and it takes none of the teammate slots (`peerSlots`), which are for the messages of Chats. One the owner accepts on the host (`r`) is marked `typed` there and starts at once. `typed` is still sent, for hosts on ELU up to 0.1.33.
- An approval answered on either machine is answered once: the approval file takes the first answer, and the next `approvals` event drops it on the viewer.
- A message of the owner's to a session that has not run on the host yet is never left unsaid: a `waiting` event carries `list: [{at, text, state, reason?}]`, all that wait now, oldest first, each `text` whole. `state` is `turn` (the session works, and reads it when its turn ends), `queued` (with the conductor's `reason` when it gave one, such as no free slot), `starting`, `stuck` (no conductor has run for 15 seconds to take it; the host starts one again, at most every 30 seconds) or `blocked` (it could not start, with `reason`). One that waits for the owner's yes on the host is `blocked` with the `reason` "Waits for a yes on @host.", which is all an ELU up to 0.1.33 reads, and says `yes: true` beside it: a newer viewer shows it as "waits for a yes" and never says to send it again. A run that waits the same way says `yes: true` in its `state` event, and its row is a waiting one, not a failed one. `computer` is the key of the computer that sent the message, when another computer did: every other viewer reads it as that computer's person, not as "You". The event is sent when the list changes, and never for a session that has had none, so an older viewer gets no event it does not know. A host on ELU 0.1.29 or later sends every message whole and every one of them: where a viewer on ELU 0.1.28 or earlier would read less (it keeps 20 of them and 4,000 characters of each), the `waiting` event carries that list, cut to what such a viewer reads (20 rows, 4,000 characters of each text and of an answered aside), with `held: true`, and a `held` event follows with the whole list as JSON text in `list`, in pieces of 60,000 characters, the rest in `held+` events (`list, more?`). A newer viewer takes the list from the `held` events and passes over a `waiting` event marked `held`; an older one ignores `held` and `held+` and keeps the `waiting` list it knows. A run that waits to start with no session yet is listed with 4,000 characters of its message; the session followed for it then carries the whole message in a `message` event (`text, more?`), the rest in `message+` events. The viewer shows each at the end of the session's chat, right above the message box, in the order sent, with why it waits, and draws nothing under them. The steps of the turn at work are right above them, the session's Task sits after the reply that proposed it, and what is about the session and not about a moment of it (where it runs, that the viewer is catching up with it) sits above its first message. The conductor runs the message whatever ELU window is open on the host, a view-only one or none.
- A `state` event also carries `model` when the host knows it: the name of the model the session's next message goes to, as the host's own message box names it. The viewer's message box shows it (Message Opus 5.5 on @devbox). With an older host, which sends none, the box names the model of the session's newest reply, or says the session.
- `always` (only with `allow`) is `a` pressed on the viewer, for this project. The host makes the rule from its own approval request, as its own `a` would (`keepOffer`, `keepRule` in `lib/permission-rules.mjs`), saves it in its own rules, allows the approval and anything else waiting that the rule covers in a session of the owner's, and returns the rule in words as `kept`. `always: "all"` from another computer is refused ("Keep the rule for this project. A rule for all projects is kept on @devbox itself."): it would reach projects that computer does not share. Where the host offers no `a` (the never list, a removal, an MCP tool, a session another computer or a teammate started) it refuses. The viewer offers `a` only for an approval whose event carries `always`; an older host sends none.
- A session with `origin.kind` `mine` was started from another computer: the owner's saved rules do not answer for it (the defaults and its team's rules do), and it takes none of the owner's session commands. ELU up to 0.1.33 made it the owner's own; such a session made then is a member's now.

Every session of a shared project, not only the ones started from here:

- `elu.remote.list` lists every session on the host of the projects it shares with that computer, whoever started it: its owner by hand, a schedule, a bot, a teammate's message, or another computer. Nothing of any other project is listed. A teammate's question (an ask or a review, answered in Chats) is not listed, an archived session (below), nor is one that neither works nor waits now (a question, a Task to approve, an approval) and has done nothing for a week; such a session leaves the list as `gone`. `projects` is every project there shared with that computer: `{id, name, repoId, home, teams?}`, where `teams` is the projects it is of the teams both computers are on (a team's id for its first project, `<team id>:<id>` for another, [A shared project](#a-shared-project)), and `id` is 16 hex characters of the folder's hash, `repoId` is the hash of its normalized `origin` URL (as for shares) or null, and `home` says it is the home folder. Each session is `{ref, project, title, state, at, createdAt, question, error, plan, approvals, by, who, repoId, since, remoteId?, standup?}`: `ref` is `<project id>:<task id>`, `at` its last activity, `since` where its row in the host's own Sessions list counts from (`{run: true, at}` for a turn that works, counted up from the start of that turn as `0m07` or `1h02`; `{at}` for anything else, said as how long ago: the approval asked, the owner's message that did not run, or its last activity), so the viewer's row shows the time the host's row shows (one function decides both: `rowSince` in `lib/kanban.mjs`, drawn by `rowTime` in `lib/board.mjs`; a host on an earlier version sends none, and a turn that works there counts from the start of its run when the viewer follows it, else from when the session was made), `plan` `{state: "proposed", title}` or null, `approvals` what waits now (as in the `approvals` event), `by` one of `you`, `schedule`, `bot`, `teammate`, `mine` (a schedule's run is `schedule` from its start; one an earlier version started, once the schedule has kept its number), and `who` the teammate's or the bot's name. A session another computer started is listed to that computer with `by` as it was; to any other computer, `by: "mine"` reads `teammate`. The answer says `mineByPeer: true`, so an ELU up to 0.1.33 reads no `teammate` session as its own by name. `repoId` is the repository the session works in, found as the Kanban finds it (`lib/kanban-repos.mjs`: the repository its edit runs in, the one its Task names, the project or the session's folder when it is a clone, else the project's main repository, picked from every session of the project, archived and older ones too), as the hash of that clone's normalized `origin` URL like the project's `repoId`, or null for none. An older build sends no `repoId`; the viewer keeps it only as 64 hex characters, else null. `remoteId` is sent only to the computer that started that session. `standup: false` marks one a standup would not ask there ("Standup" below). Newest first, at most 100 a page; `next` is the cursor for the next page (`after`).
- The chat of the bot that oversees the owner's sessions ([Orchestrator](orchestrator.md)) stays on its computer. That holds under every name that bot has had: the host keeps each one and never drops it, and when it cannot read its bots it counts every bot as one. `elu.remote.start`, `elu.remote.files` with `start` and a `copy` answer of `elu.remote.check` are refused with "Only the owner writes to @orchestrator, on the computer it runs on." when the session's bots name that bot. It and a waiting start of it are not listed; a watch, rename, archive, delete or check of it is answered "That session is not on this computer."; a watch made before shows the state `gone` ("The chat of @orchestrator stays on that computer."). What that bot replies, runs or asks in any session is left out of that session's events and approvals. A session the bot started lists with `by: "bot"` and `who` its name, and a note of the bot that waits is sent in `waiting` with `from: "@orchestrator"` and `overseer: true`; the viewer shows it under that name. That chat is also no card of the Kanban read from another computer (`elu.remote.board`), no card or Task told to teammates, no status row and no session of a Standup, and that bot's runs, replies and questions are no part of any record sent. While that bot is at work in a session, the session reads as working, with no role named.
- `cursor` is the host's clock when it listed. Given back as `since`, only sessions that changed after it are sent, and `gone` names the ones that left. A cursor from before the host's daemon started, or more than 10 minutes old, gets everything again with `full: true`. The viewer asks for everything when the host connects, then every 3 seconds for what changed. A list of several pages takes one page a tick, at most 10, and is kept in `peer/remote/machines/<key>.json` once its last page is in.
- What the viewer asks a host on its own (lists and catch-ups) stays within 8 requests in 10 s per host, and watches made by the cursor within 14 with them, under the connection's limit of 20. A watch past that is refused for a moment ("<name> is busy") and asked again 5 s later. What the owner does (send, stop, answer, a watch by key) is never held back, but counts.
- `elu.remote.watch` makes a listed session one the viewer follows: from then on it has numbered events, and `since`, `send`, `stop`, `answer` and `task` take its `id` as for a session started from the viewer. The `id` is the UUID made from SHA-256 of `watch`, the viewer's key, the host's key and `ref`, so both sides know it before the answer. A watch lasts a week after its last event or watch. A command or catch-up to a watch the host let go is answered "That session is not on this computer.": the viewer watches it again once under the same `id`, keeps its view in place and starts its events over from the first, and sends the command again. A view whose listing shows activity more than 2 minutes after its last event, once for each such listed change, catches up the same way: its events are on their way (a session quiet there for 10 minutes is looked at every 30 s, and listed every 3 s), it missed events without seeing a gap, or its watch was let go. A view goes only when the watch itself is answered "That session is not on this computer.", or when a catch-up finds the watch let go of a session its computer no longer lists.
- Sessions on the viewer shows, after its own, a heading per computer on a shared project ("On devbox · ana", "· offline" while it is offline): the sessions there of the project open here, by its team folder, and the ones started from the viewer, newest first. With none of them, the heading says "No sessions of this project. Projects lists its others." when that computer has sessions this project does not show, else "No sessions yet." Each row takes its time and its place from the listing. What waits for its owner there in that project (an approval, a Task to approve or a question) also shows under Needs you, marked "on devbox". A shared project's row in Projects counts, beside its own sessions, the ones on each other computer that the heading shows while it is open ("22 sessions · 22 on @devbox"), and its last activity is the newest of them. Archived ones are not counted. A row is watched when the cursor rests on it for 300 ms, and not while its computer is offline ("<name> is offline. What it listed last is shown."). A watch that failed is asked again after 30 s, not on every draw.
- A shared project that this computer has no folder of shows its sessions only while it is opened from Projects ([Projects a teammate shares](#projects-a-teammate-shares)).
- A computer whose build answers `elu.remote.list` with Method not found, or that does not say `remote: 1`, shows "Update ELU on <name> to see its sessions here." and is asked again after 10 minutes.
- Both methods are refused, as the others, unless the sender shares a project with the host: that key is listed, and can watch, only that project's sessions. Nothing else about a computer (its other projects, its top agents, its archived sessions) is listed, watched or sent.
- `elu.remote.rename` and `elu.remote.archive` rename, archive or bring back a session on the host from another computer on the project, under its access rules there (`/rename`, `/archive`, and `e` and `c` on its row; ELU 0.1.26 also brings one back with `u` on its row under `/archived`), with the host's own code for them (`setTitle` in `lib/state.mjs`, `closeSession` and `reopenSession` in `lib/kanban.mjs`): the same rule for a name, and a session at work is not archived ("\"<name>\" is running. Stop it first with /stop."). One brought back that the owner had checked Done comes out of Done with its Task open again, as Shift+← brings it. The session is named by its `ref` from the list, or by the `id` of one the viewer follows; one that has not started there is refused with "This session has not started yet. Try again once it has." `title` in the answer is the name someone chose (null when none), `titleBy` who chose it, and `shown` what lists show. The host lists the change at once and sends a `state` event to every computer that follows the session. A host says `edit: 1` in its `elu.hello` when it takes both. To one that does not (ELU 0.1.25 and earlier) nothing is sent, and the viewer says "@<name> needs ELU 0.1.26 to rename its sessions." (or archive, or unarchive).
- Archived sessions are each computer's own: none is listed to another computer, a watch of one is refused with "That session is not on this computer.", and one archived since a cursor is in `gone`. `/archived` lists only the viewer's own archived sessions, and the line at the bottom of the list counts only those. A session the owner checked Done there is in Done, not archived: it is not listed to any viewer, as Sessions there leaves it out, and one checked since its cursor is in `gone`. A session listed with `named: true` has a name someone chose, which `/rename` there opens with.
- `elu.remote.board` reads a shared project's board on the host with the host's own Kanban code (`lib/peer/remote-board.mjs`), and `elu.remote.boardAct` does there what the same key does on a board here (n adds to To do, Enter edits a To do card, x removes a card, Shift+→ starts a To do card, Shift+← reopens one in Done), under that project's access rules there. The reply fits one peer message: while it is too long, a busy board leaves out the Tasks of its Done cards and then those cards, the oldest first, then the same in the other columns. A session under Needs you goes to Done only through the owner's check, as here (`moveToDone` in `lib/owner-check.mjs`). The host refuses what its own Kanban refuses, in the same words, and both methods for a project it does not share with that computer. A host says `board: 1` in its `elu.hello`; one that does not (ELU 0.1.25 and earlier) is never asked.
- `elu.remote.delete` deletes archived sessions on the host for good from another computer on ELU 0.1.26, of a shared project and under its access rules there (`x` on an archived row or its "Archived on <name>" heading, and `/archived clean` there). From ELU 0.1.27 a viewer sends none: `/archived clean`, and `x` on an archived row or on the Archived heading, clean up only that computer's own archived sessions, and each computer cleans up its own. The host still answers a viewer on 0.1.26, with its own code (`deleteSession` in `lib/session-delete.mjs`). `check` only says what each would lose that is on no remote. `learn` first runs the lessons run there, on that project's model, and saves to that project's memory (`context.md`); if it fails, nothing is deleted. It stops on `{stop: true}` from the same computer, or when that connection closes. `keep` leaves work on no remote in its folder and on its branch. A session the owner checked Done is in Done, not archived, and is never deleted: it is refused with "\"<name>\" is in Done, not archived." (from an ELU 0.1.26 viewer that still lists it as archived too). After the run each session is checked again: one that is no longer archived is not deleted (in `failed`, "It is no longer archived."), and work on no remote that appeared while the run read, which nobody was asked about, is kept as with `keep`. `seen` (optional, each `{ref, commits, edits}`) is what `check` said and the owner was told: without `keep`, a session that holds more work on no remote when the delete arrives is not deleted (in `failed`, "It now has 1 commit not pushed. Clean it up again to be asked about it."), and is not read by the lessons run. With or without `seen`, the check after the run measures from the work as it is when the delete arrives, never from what he was told: one that held less by then keeps the work that appeared while the run read. A viewer that sends no `seen` gets only that check, as before. A viewer on 0.1.26 sends nothing to a host whose hello does not say `clean: 1` (ELU 0.1.25 and earlier), and says "<name> needs ELU 0.1.26 to delete its sessions."
- `elu.remote.check` is the owner's check of a session that ended on the host (`/done`, or Shift+→ on its card under Needs you), with the host's own code (`lib/owner-check.mjs`): without `answer` it returns the Task's goal and objectives with the agent's marks and evidence, and a session at work with no Task is refused before anything is shown ("\"<name>\" is working. Check it when it stops."). One at work with a Task comes with `working: true` (ELU 0.1.31 and later; an earlier host refuses it as above), and so does its Task with `look`: its one answer is `goal`, which changes the Task at once without stopping the turn, and the answer's `takes` says when the turn is told: `turn` at its next step, `end` when it ends (it takes no message while it works), `soon` not known yet (a goal and objectives the Task has already, or a turn still on the conductor of a build from before an update, is refused); while `done` and `copy` are refused as before; `done` moves it to Done there, `goal` gives its Task the new goal in `text` and carries on, and `copy` starts a copy with that goal and moves it to Done. The new goal is the owner's own words, taken whole however long and with as many objectives as he wrote, one a line; one too long for one line on the link goes first in `elu.text.put` pieces and the request carries `longText` in place of `text`, as `elu.remote.send` does. A host says `whole: 1` in its hello when it takes a goal of any length (ELU 0.1.29 and later). One that does not refuses a `text` over 4,000 characters: the viewer sends such a host 4,000 at most, and for a longer goal says "<name> needs to update ELU to get a message this long." and sends nothing. The list marks a session that waits for the check with `check: true`, and a card carries `check` (how it ended). A host says `check: 1` in its hello; to one that does not, nothing is sent and the viewer says "@<name> needs ELU 0.1.26 to check its sessions."

### Instructions and memory

A project's instructions and memory (`.elu-code/instructions.md` and `context.md`; the app calls the context the project's Memory) are the same on every computer that has the project, as its tasks are, and every model and bot there reads them each turn. The daemons of two computers on a team send each other what each project shared with that team has, both ways (`lib/peer/notes.mjs`), and nothing of any other project: the same for every computer, the owner's own included (see [A shared project](#a-shared-project)).

- `hello` carries `notes: 1`. To such a computer, `elu.notes` (notification) `{notes: rows}` carries every project here shared with it, on connect, within a tick (2 s) of a change, and every minute in case one was dropped; a long list goes in parts (`elu.list.put` with `list: "notes"`, see [Long messages](#long-messages)). Each project is the JSON of `{id, name, repoId, home, links, teams?, notes}` cut in rows `{id, seq, of, data}` of at most 50,000 characters, so a long text never makes a row too long for a connection; ELU sets no limit on the text. `id`, `repoId`, `home` and `teams` are as in `elu.remote.list`. `notes` is `{instructions: {text, at}, own: {text, at}, learned: [{line, since, at, on}], org?: [{line, since, at, on}]}`: the instructions, the owner's own text of the memory (`context.md`, all but its "Learned from you" and "Organization" sections), every line of the "Learned from you" section, and, for a project whose Organization section has or had a line, every line of that section; a line taken out is kept as `on: false`. `at` is when that text or line came to be, in milliseconds; `since`, when the line was first learned. `org` is left out when there is no such line, and an ELU from before the section reads past it.
- Only text in force on the sender goes: what the owner approved there (`lib/project-trust.mjs`), never a file Git changed that waits for his answer. What came is kept in `peer/notes/from/<key>.json` until that computer sends again, so a computer that was off is caught up on connect.
- Which project there is which here: the one that is the project of the same team (`teams`), as the invite and the join made it, and no other. `links`, which an ELU up to 0.1.28 made by hand, is still sent as it was, for older computers, and is not read here; a project of the same repository or the same name that no team shares is not put together. The project's settings show, read only, the computers that have it: "Also on @devbox, @studio".
- Each tick, each pair of the same project is put together when either side changed since (`lib/project-notes.mjs`), and written as a save on this computer writes it, approved: it is the project's own edit, as a teammate's is. Each text (the instructions, and the owner's own text of the memory) is taken from the other computer when only it changed since the two last agreed. When both changed it, the newer edit wins; the other is kept in `.elu-code/history/<instructions|context>-<date>-<time>.md` in the project (the folder ignores itself for Git), once, and the app says it once: "Instructions of ELU changed here and on @devbox: the newer, from @devbox, is in use. The other is in ~/projects/ELU/.elu-code/history/instructions-2026-11-14-101500.md." The learned lines are a set: the newer change of each line (added, or taken out) holds on both, a line taken out wins a tie, and the section is in the order the lines were first learned.
- **Organization.** The memory's `## Organization` section holds findings about the organization that the owner accepted from the bot that oversees his sessions ([Orchestrator](orchestrator.md), `lib/org-section.mjs`): at most 20 lines of at most 200 characters, each ending with the ids of the facts it stands on, such as `[f12]` (on a computer with a peer key the id carries the first 8 hex characters of that computer's key, `[f12@1a2b3c4d]`, and an id with none is read as this computer's), under one fixed sentence that tells every agent these are findings with sources, not the owner's orders. It is kept as "Learned from you" is: the same lock, the same trust record, and the same merge, a set of lines in `org` where the newer change of each line holds on both and a line taken out wins a tie. The fact ids name facts on the computer that saved them; facts themselves never leave it. A merge keeps the section within its 20 lines of 200 characters: the lines here first, then the newest that fit, each written as a `- ` list item; how many were not added is said once. An id with no tag never travels: lines leave with this computer's tag on such ids, and a received line's untagged ids get the sender's tag. A received line that does not end with fact ids is dropped. A line found with no record of it counts as changed at 0, so another computer's change of it wins. An ELU from before the section sends it inside the owner's own text; it is read here as the section, not as his text.
- A file that changed some other way (a pull of a teammate's change, say) is never written over: it still waits for his answer, and the text from the other computer is the one in force meanwhile.
- An edit of the Memory in the Projects tab keeps lines learned while it was open, here or there; only the lines he took out go.
- A computer whose hello lacks `notes: 1`, or `shared: 1` (ELU 0.1.28 and earlier), is sent none, and what it sends is not taken.

### Files

A message to a session of a shared project on another computer can take files and folders from this one, when that project is Auto there. Every computer on the project the same; a session another teammate's message started takes none.

**What is sent**

- A message typed to such a session that names files or folders here (absolute, `~/`, quoted, or with spaces escaped as a dropped file is) asks one line first: "Send 14 files (2.1 MB), including 1 key file, from this computer with this message?". y sends them with the message, n sends the text alone, and Esc sends nothing: the message stays in the box. `/send PATH...` sends files alone after the same line. Anything you can read may go, key files included: the line names them, and they go only to the session you write to.
- A folder goes whole, except its `.git`, a link that leads out of it, a link to a folder in it, and anything that is not a file or a folder (the line says how many were left out). ELU's own state folder never goes.
- At most 5,000 files and 200 MB a send. Over that, the line says so and offers the text alone.
- The message that starts a session there (`@name` first in the New session box) asks the same line, and y starts the session with them: it reads them from its first turn.
- A Claude Code session of yours (its relay, `elu-code-approval`) has two tools: `list_other_sessions` (each computer on a shared project, and its sessions' id, title, state and the question or approval they wait on) and `send_to_session` `{session, paths, message?}`. A send reads only what that session may read: never ELU's state, the home's secret folders or an untracked file whose name may hold a secret, and in Approve for me nothing outside the folders its turn reads (its workspace, the folders added with `/permissions folders`, and the home only in a turn that reads across it). Paths are compared by what they are on disk, and those closed folders and secret names without case, so another spelling of the same file is the same file. Each file is copied only if it is still the file that was checked, never through a link. A teammate's session on that computer, such as a handoff accepted there, is not listed and takes no files. In Ask for approval each send is an approval for you, naming the session, its computer and the paths. Sessions on other models do not have these tools.

**On the wire**

1. The app or the tool copies the files to `peer/files/out/<set>/` in the state folder, each with its SHA-256. The daemon sends only from there.
2. One send is one stream: its list as a JSON line (`{items: [{name, written}], files: [{path, size, sha256}]}`), then each file's bytes in that order. It goes in pieces of 700 KiB with `elu.remote.files` `{id, send, seq, last, size, data}`, `data` base64, the message as `text` on the last piece. Pieces count toward the same request rate as the other requests to that computer, and one turned away as busy is sent again shortly.
3. The host takes pieces only from a key on a project shared with it, for a session of that project that key may write to under its access rules (as `elu.remote.send`), that has started, and that no other computer's message started ("That session answers another computer's message. Files go only to the project's own sessions."). It stages them in `peer/files/in/<sender key>/`, at most 2 sends from one computer at a time, and removes a half-sent one after 10 minutes.
4. With the last piece in, the list is checked again (the same caps; each path relative, no `.` or `..`, no `.git`, no name given twice) and every file is written new (0600, folders 0700, never through a link) and checked against its SHA-256. On any fault nothing stays and nothing reaches the session.

**Where they land**

- In the session's inbox, `elu-code/inbox/<project id>-<task id>/<time>-<computer>/` in the data folder (`$XDG_DATA_HOME`, else `~/.local/share`): outside the state folder, which no session may read, and outside every project and worktree. Where that folder is inside a Git work tree that does not ignore it (a home folder that is a repository, say), nothing is received, so no session there commits what landed: the sender is told to add it to that repository's `.gitignore`. The inbox is added to the session's folders, as `/permissions folders add` would, so the session reads it in every mode.
- The message continues the session as one typed there, each path it named pointing where that file or folder landed, and ends with "Files from @laptop: 14 files (2.1 MB) in <folder>". The sender sees "Sent 14 files to the session on @devbox."
- Files with the message that starts a session land in `elu-code/inbox/<project id>-<session id>/<time>-<computer>/`, one of its folders from its start. The sender sees "Started on @devbox in shop with 14 files."
- A message from another computer goes as it was written. A path it names on this computer in a folder no session reads (a screenshot under `~/Library`) is not copied for the session: only what is sent with it as files lands here.

## Pictures

A message you type to a teammate or a channel takes along the pictures it names.

**What is sent**

- Write or drag a picture's path into the message box. A path with its spaces escaped (as a terminal writes a dropped file), a quoted path and a `~/` path all work.
- The path in the text becomes the picture's file name. The teammate never sees your folders.
- A file counts as a picture when its first bytes say PNG, JPEG, GIF or WebP. Its ending does not matter. Any other path stays the text it was. Nothing else in the file is checked, and it is sent unchanged: what a photo records about the place, the device and the time goes with it.
- Only a message you typed carries pictures. A model's draft (sent by hand or by itself), a review, the command line and the local A2A endpoint never attach a file, so a model cannot send a file out by naming its path.
- A path in text you pasted into the message box is a path you typed. The line that says how many pictures went (`with 2 pictures`) is shown after the message is sent.
- A picture in a folder that holds secrets (`~/.ssh`, `~/.aws`, `~/.config` and the rest of that list, and ELU's own state folder) is refused. `~/Library` is the one folder of the list that stays open, because screenshot tools save there. A hard link in another folder to a file in such a folder is not recognized, and is attached.

**Limits**

| | limit |
|---|---|
| one picture | 8 MB |
| pictures in one message | 4 |
| all pictures in one message | 16 MB |

Over a limit, the message is not sent, it stays in the message box, and one line says why, for example `shot.png is 14 MB; a picture can be up to 8 MB.`

**On the wire**

1. The app you typed in copies each picture to `pictures/out/<set>/<n>` in the state folder. The daemon sends only from there, never from a path in a command.
2. Before the message, the daemon sends each picture in pieces of 700 KiB with `elu.picture.put` `{id, seq, last, size, sha256, data}`. `data` is base64, so a piece stays under the 1 MiB frame. Pieces count toward the same request rate as everything else, and one message with pictures goes to a teammate at a time.
3. The message then names each picture as an A2A file part by reference: `{url: "urn:elu-code:picture:<id>", filename, mediaType, metadata: {"urn:elu-code:a2a-ext:peer:v1": {size, sha256}}}`. A file part does not count toward the text limit.
4. The Task that `SendMessage` returns says how many pictures were kept, in its extension metadata as `pictures`.

**On the receiving side**

- Pieces are taken only from a teammate who is not muted. Each picture is checked again: its first bytes, its size and its SHA-256.
- A finished picture waits in `pictures/in/<sender key>/` for the message that names it. One that waits longer than 10 minutes is removed.
- When the message is accepted, its pictures move to `pictures/kept/<sender key>/<task id>/1.png` and so on: a folder only you can read, names made here, never the sender's path. The sender's file name is kept as cleaned text. A kept file is known as a picture by its first bytes only; it is readable by you alone (0600) and ELU never runs it.
- In Chats, the row says how many pictures came and how large (`@kim asks you with 2 pictures (1.5 MB)`), and the opened message lists each name and size. The sender's row says `with 2 pictures`.
- A refused message keeps no pictures. Kept pictures are removed with the message's record.
- Caps, so a teammate cannot fill the disk: 32 MB or 16 pictures on their way from one teammate, 64 MB kept from one teammate, 256 MB kept in all. Over the first, the sender tries again later. Over the others, the text arrives without the pictures and the sender's row says so.

**When the question runs**

- The pictures are copied to a folder of their own under `elu-code-pictures` in the temporary directory. The folder is yours alone (0700) and holds only that question's pictures.
- A question run reads the shared project and, when the message came with pictures, that one folder. Nothing else changes about what a teammate's question can read.
- The pictures are named inside the teammate's data block, so the model treats them as the teammate's material and never as instructions.
- The copies are removed when the run ends. While it runs, another session of yours that can read the temporary directory could read them.
- If the copies cannot be made, the model is told the pictures' names and that it could not see them.
- A message you take on as your own session, in a mode you pick, gets the same copies as paths in the teammate's data, like a picture you name in your own session. Those copies stay in the temporary directory, as the copy of your own picture does.
- With another model than Claude, a teammate's message can only be taken on as your own session, so that is the one way its pictures reach that model.

**Older builds**

- A teammate on a build from before pictures answers `elu.picture.put` with "Method not found". The sender then sends the text alone, with the pictures' names in it, and the row says `@kim's ELU can't take pictures yet. The text went without them.`
- A message from such a build has no file part and is taken as before.

## Long messages

A question, a review, a handoff or a result of any length goes to a teammate whole. ELU sets no limit of its own on it; only the model that reads it may say it is too long.

- A text that fits in one line on the link (768 KB as JSON) goes inside the message.
- A longer one goes first, in pieces of 700 KiB, with `elu.text.put` `{id, seq, last, size, sha256, data}`, as pictures do. The message then names it with a part `{url: "urn:elu-code:text:<id>", mediaType: "text/plain", metadata: {<peer extension>: {size, sha256}}}`. The receiving side checks the size and hash, puts the whole text back in place of that part, and then reads the message as usual.
- What the receiving side holds for its disk, not for the model: a text is at most 64 MB, a teammate has at most 8 texts and 128 MB on their way at once (more is answered as a rate limit, which the sender retries), and pieces not used within 10 minutes are dropped.
- The thread (`peer/threads/<contextId>.jsonl`, one hash-chained line per message) keeps each text whole on both sides, and the thread screen shows it whole. A thread of any length goes on recording. A teammate's message, answer or result is written to the thread before its row shows it, so a row never shows one the thread screen does not have. Its line carries an `id` (the `messageId` for a message or a result, the task for an answer): when the line could not be written nothing else is kept or queued, the teammate's ELU sends or is asked again, and a line that is there already is not written twice. ELU 0.1.19 cut a text there at 160000 characters and wrote nothing more to a thread over 4 MiB.
- What a model writes has no length limit of ELU's either: the result of a run, a question it asks the owner, a review comment or its response, and an ask it drafts for a teammate are read whole, from every vendor. ELU 0.1.19 failed a run whose result was over 4000 characters with "The run returned an invalid outcome or summary.", so a long result never reached the teammate.
- A teammate on ELU 0.1.19 or earlier refuses a question over 16000 characters, or a review over 160000, and does not know `elu.text.put`. The row then says `@kim needs to update ELU to get a message this long.`
- A message to a session of a shared project on another computer goes the same way: a new session, a message to one, and a message sent with files. The pieces go first with `elu.text.put`, which takes them from a computer on a team with this one that it has not muted, and the request (`elu.remote.start`, `elu.remote.send`, or the last piece of `elu.remote.files`) carries `longText: {id, size, sha256}` in place of `text`. The host puts the whole text in its place before it reads the request. A piece or a request whose answer was lost is sent again and taken once. A computer on a build that does not know `elu.text.put` gets nothing, and the line says `@devbox needs to update ELU to get a message this long.`

## Roster

- **Ops.** `{teamId, id: sha256(canonical body), type, by: hexKey, at, body, sig}`. `sig` is ed25519 over the canonical JSON of everything except `sig`; canonical means sorted keys and no whitespace.
- **Types.**
  - `create`: by the founder; body `{name}`. The teamId is the id of this op.
  - `admit`: body `{key, name, role: "member"|"admin", invite}`. `invite` names the invite: sha256 of `short:` followed by the joiner's verifier key for a short code, sha256(secret) for a long one.
  - `remove`: body `{key}`.
  - `role`: body `{key, role}`.
  - `relays`: body `{keys}`.
  - `leave`: by the member leaving.
  - `channel`: by a member, with body `{id, name, members}`.
    - `id` is 16 hex characters.
    - `name` is 1 to 30 lowercase letters, digits, `-` or `_`. It starts with a letter or digit, and `general` is taken.
    - `members` is a list of up to 20 distinct keys.
- **Merge.** A pushed op is stored only if the fold applies it. Dropped: ops over 10 minutes in the future; every op from a key the receiver's log shows out of the team now (whatever its `at`); and every op from a key that sorts at or before that key's latest leave or removal in the receiver's log, even after the key came back. Two logs can then differ by refused ops; sync keeps offering them and the receiver keeps refusing.
- **Fold.**
  - The log is a grow-only set. State is computed by sorting ops by `(at, id)` and applying them in that order.
  - An op is applied only if, at that point in the fold, its signer holds the needed role: the founder for create; an admin for admit, remove, role and relays; anyone for their own leave; a member for a channel op, under the channel rules below.
  - Removal wins: from a key's removal or its own leave, its ops are ignored. The founder cannot be removed, leave, or change role.
  - **Coming back.** An admin's later `admit` of that key (a new invite, redeemed as usual) brings it back with the role, name and join time of that admit. Ops it signed before it went out stay applied; ops that sort between its exit and the new admit are not applied; ops that sort after the admit apply under its new role.
    - Why this is safe with timestamps that the signer picks: the fold judges an op by where it sorts, never by when it was signed. A returning key cannot backdate an op to when it held its old role, because every machine that has the exit refuses, at merge, any op of that key sorting at or before it. An op dated into the window between exit and admit is not applied. An op signed while out and forward-dated (at most 10 minutes, the merge limit) past the new admit applies only under the role that admit gave, the same as an op signed after coming back. An admin's `admit` is stamped after the newest op that admin has, so it sorts after the exit it answers.
    - A machine that never got the exit can still take a backdated op from that key, as it could before; it is refused by every machine that has the exit, and the logs differ by that op.
    - A teammate on 0.1.5 or earlier refuses the new `admit`, so it keeps the returning member out until it updates.
  - The fold returns `channels: [{id, name, members, createdBy, createdAt}]`, oldest first.
- **Channels.** A channel is a named group inside a team. `#general` is everyone on the team and needs no op.
  - One `channel` op sets the whole channel: its name and its members. An op with no members deletes the channel.
  - Any active member may create a channel that lists them.
  - A channel's members and the team's admins may change it.
  - Every key listed must be an active member of the team.
  - No two channels share a name.
  - A member who is removed from the team, or leaves it, drops out of its channels. A channel with nobody left is gone, and its name is free again.
  - Limits: 50 channels per team, and 200 channel ops per signer. An op past a limit is not applied.
  - A channel op syncs like every other op, so the people added get the channel from any teammate.
  - A teammate on an older build refuses the op and sees no channels.
- **Leaving and removing.** `/leave` or `elu team leave` appends the member's `leave`; `/remove @name` or `elu team remove NAME` appends an admin's `remove`. The founder cannot leave and cannot be removed. Both go through the daemon, which is started for it when it is not running; a daemon started for it first waits, until 10 s after its start, for the team's teammates to connect. The op is then pushed at once to every teammate online, the one removed included, before their connections close (it waits up to 5 s for them). The machine that left drops the team from Chats and forgets which of its projects was that team's, so coming back shares nothing until the owner shares again.
  - A machine that was offline gets the op on its next connection. Its hello still lists the team as shared, while the other side's log shows one of them out: that connection serves nothing but an invite exchange; the side that has the op pushes the ops the other lacks up to that exit (as in sync, never an op that sorts after it), and the connection closes once the other side has it, or after 30 s. Sync applies the same cap on any connection, for a team where one of the two is out.
  - A leave no teammate took at once is noted in `unheard.json` (`[{team, op}]`, written before the leave is sent). While a row is there, the daemon keeps running, also on no team, and dials that team's other members; the first of them to connect is given the leave as above. The row goes once a teammate has taken the op, once every other member's hello shows it already counts this machine out (an admin removed it, say), or once this machine is back on the team. The app and the CLI say when no teammate was told.
  - A member whose leave nobody heard can still come back with a new invite: it sends that team's ops up to its leave (at most 64) with `elu.invite.prove`, and an inviter that still lists it on the team takes them in before the admit. An inviter on an earlier build ignores them and refuses with `You are already on this team.` until it hears the leave.
  - A machine on no team after a leave a teammate took, or after it hears it was removed, stops its daemon at once.
  - Without the networking packages the op is written to the log here. A remove goes out the same way once the daemon runs; a leave is noted as unheard, and goes out once the daemon can start.
- **A team of one.** The first `/invite` makes a team so there is a code to send. A machine that then joins someone else's team would keep its own beside it: a second #general with only itself in it.
  - So a team this machine made, whose log holds nothing by anyone else and nobody's `admit`, is closed once the machine is on a team that has, or had, someone else on it. The daemon does it as a join lands, and answers the `join` with `closed: [{id, name}]` when it closed one. The app and `elu join` say so in the line that says it joined, and when the machine is on more than one team after the join, that each has its own #general.
  - The app does the same once as it opens (`solo-check.json` notes that it looked), for a machine 0.1.19 or earlier left on both, and says it in one line. After that look, a team made on purpose with `elu team create` stays until a join.
  - Closed means the team's folder moves, whole, from `teams/` to `closed-teams/`. Nothing is deleted, no version reads it as a team, and its open invite codes stop working, since a code is answered only for a team this machine is on. Its project is no longer shared with it and its setting is forgotten, as after a leave. Nobody is told: nobody else ever had its log.
  - Never closed: a team that has or had anyone else on it (a teammate, another computer of the same owner, someone who left or was removed), a team whose invite somebody used, and a machine's only team.
  - `/invite` on a machine that is on a team makes its code for that team and never makes another: with several teams it can invite to, it asks which. Only an admin can add someone, so a member is told who made the team.
- **Sync.**
  - On every connection, each side compares `{seq, head}`, where head is the sha256 of the sorted op ids.
  - The side with ops the other lacks pushes them with `elu.roster.push`. The receiver validates every op and drops invalid ones.
  - A team both are on that the other side's hello left out (it did not know this machine was on it yet) is synced too.
  - New ops are also pushed to every connected teammate, including ops another process (the CLI) wrote to the log.
- **Invites.**
  - **The code.** 12 characters in three groups of four, such as `k7qm-x2pd-9fhw`, drawn with `crypto.randomBytes` from 31 characters: the digits 2 to 9 and the lowercase letters without i, l and o. That is 31^12 codes, about 59.4 bits. A code names no team and no key. It is single use and expires after 24 h by default.
  - **Reading a code.** Whitespace anywhere (spaces, tabs, line breaks), case, dashes, quotes around it, and `/join` or `elu join` in front, once or twice, are ignored.
  - **Keys.** `master = scrypt(code without dashes, salt "elu-code invite code", N = 2^16, r = 8, p = 1, 32 bytes)`, about 64 MiB of memory and a fraction of a second per code. Then HKDF-SHA256 of `master` with no salt and the info strings `elu-code invite topic`, `elu-code invite inviter proof` and `elu-code invite joiner proof` gives, 32 bytes each:
    - `topic`, the Hyperswarm topic;
    - `prover`, the inviter's HMAC-SHA256 key;
    - `seed`, an ed25519 seed whose public key is `verifier`.
  - **Stored.** The inviter's `invites.json` (mode 600) keeps `{hash: sha256("short:" + verifier), expiresAt, usedBy, topic, prover, verifier, project?}`, and `usedAt` once used (`project`: the id of the team's project the code was made in when it is not the first, see [A shared project](#a-shared-project)): not the code, and not `seed`, so the file alone cannot be used to join. The prefix means no long code's secret hashes to a short row's `hash`, so a 0.1.3 daemon reading the file does not take the verifier as a secret.
  - **Finding the inviter.** While an invite is unused and unexpired, the inviter's daemon announces on `topic` (`swarm.join(topic, {server: true, client: false})`). It stays there for 10 minutes after the invite is used, or until it expires if that is sooner, and then leaves. The joiner derives the same topic, looks it up (`{server: false, client: true})`), and tries each peer it finds there. A peer found on the topic gets nothing but the hello until both proofs pass.
  - **Proofs.** Both cover the canonical JSON `{proof: "elu-code invite", role, topic, joinerNonce, inviterNonce, inviter, joiner}`, where the nonces are 32 fresh random bytes from each side and `inviter` and `joiner` are the two Noise public keys of this connection (all hex).
    1. Joiner → `elu.invite.start {topic, nonce: joinerNonce}`.
    2. Inviter → `{nonce: inviterNonce, proof: HMAC-SHA256(prover, role "inviter")}`. The joiner checks it, and closes the connection if it is wrong.
    3. Joiner → `elu.invite.prove {proof: ed25519 signature with seed over role "joiner", name, exits?}`. `exits`, `[{teamId, ops}]`, is sent only for teams the joiner left without that inviter hearing it (see Leaving and removing).
    4. The inviter checks the signature against `verifier`, takes in the `exits` entry for the invite's team when its log still lists the joiner on it, then checks the expiry and that the invite is unused, appends `admit`, and replies `{teamId, inviter: its key, ops: the full log, project?}` (`project` for a code made in another project of the team, which a joiner whose hello lacks `projects: 1` is refused before the admit). The joiner checks that `inviter` is the key on the connection and that the log admits it. A key still on the team is refused (`You are already on this team.`) and the invite stays unused; a key that left or was removed is admitted again.
  - **A lost reply.** For 10 minutes after an invite is used, the key it admitted may run the exchange again and gets the same `admit` op with the full log, while that admit still stands: a key removed or gone since is refused and needs a new invite. Any other key is refused.
  - A proof that fails ends the connection. A key with 3 failed proofs in 10 minutes gets no invite answers until the window has passed. A start that names an unknown topic is refused and closed, and does not count: finding a topic costs a scrypt run either way. There is no limit on failures from everyone, since keys cost nothing and it would let anyone lock the real joiner out.
  - **Who answered.** The inviter's proof shows only that the other side knows the code. Anyone the code reached, and anyone with a copy of the inviter's `invites.json`, could answer as the inviter with a team of their own. A join makes the folder it joins in the project of the team the code was made in ([A shared project](#a-shared-project)): everyone on the team, whoever answered the code, sees the sessions in it and has its instructions and memory. `/share off` in it stops that, and `elu peers` shows the fingerprint of every member. What a join does tell is the approved Tasks of the joiner's clone of a repository a member of the team says they share, when that claim names the repository's first commit and the clone has it ([Tasks](#tasks)). Every session the joiner runs in a repository a teammate also has is also on that teammate's Kanban: its title, column, who started it and which machine ([Kanban](#kanban)). For a public repository anyone can name both. Nothing on the joiner's Kanban marks this; `/share off` in a project stops it.
  - **Long codes from 0.1.3 and earlier** still join: `elu-team:v1:` + base32 of `{teamId, inviter key, secret(32), expiresAt}`. The joiner dials the inviter's key and calls `elu.join {teamId, secret, name}`; the inviter checks `sha256(secret)` against a row that has no `topic`. A short invite is never redeemed through `elu.join`.
  - The inviter must be online for the join. Until it, neither hello names the team, since the joiner is not on it.
  - **What a join says.** The joiner looks for 60 seconds. With nobody on the topic it gives up with `Nobody answered for this code. …`. Once a computer is found, the app and the shell say `Found them. Connecting…`, and the join keeps trying for 3 minutes in all, directly and through any computer that can pass it along (see [When two computers cannot connect](#when-two-computers-cannot-connect)). It never says nobody answered for a computer that did: one that was found and could not be reached ends with `Found their computer, but could not connect: …`, with the reason, whether another computer was tried, and what works. In the app a reason too long for the status row is shown whole in a window.
  - **The daemon's version.** `state.json` carries the daemon's package version. A daemon keeps the code it started with, so when the app opens and before inviting or joining, the app and CLI restart one whose version is not their own (0.1.3 and earlier write none): a shutdown, with `enabled: false` written to `settings.json` for daemons from 0.1.5 and earlier, which honour a shutdown only then, then this copy's daemon. If it does not stop within 10 seconds, they refuse and say to try again.

## When two computers cannot connect

Some networks give every connection a new port (phone hotspots and some office and mobile networks do). HyperDHT can connect such a network to an ordinary one, but only one try every 20 seconds or so, and two such networks cannot connect directly at all. A try that fails ends at once, so a join used to give up as if nobody were there.

- **Trying again.** A join that found the inviter and could not connect tries again every 10 to 20 seconds, the pace HyperDHT itself keeps, for 3 minutes in all. The line that counts says `Found them, but could not connect yet. Trying again…`.
- **Passing it along.** A third computer both can reach carries the connection: a blind relay. It forwards packets it cannot read, since the two ends still run Noise between them. It sees both IP addresses and how much is sent.
  - Any daemon on a team carries for its teammates, in the order they connected. Its hello says so with `carry: 1`. A daemon asks only teammates it reaches directly: one it reaches through a relay itself would be no nearer.
  - A teammate asks with `elu.carry {with: key}`, and only for itself and that one key. The daemon answers `{relay, ms, online}`: the key of a relay made for the pair, how long it lasts, and whether it reaches the other key directly itself. The relay has its own key pair, `sha256("elu-code carry" + this daemon's seed + the two keys, sorted)`, and lets in those two keys and nobody else. Neither can use it to reach anyone else on the machine that carries, and it never admits a stranger: admission to that machine's own key is unchanged.
  - A grant lasts 10 minutes unless it is asked for again; whoever asked does that every 3 minutes. Once it has run out the relay lets nobody new in, and it closes when the connection on it has ended. One daemon carries at most 16 pairs, 6 for one teammate.
- **A join through the joiner's side.** The joiner asks up to two teammates it is connected to (on any team it is already on) to carry it with the inviter's key, which it knows as soon as the inviter is found. After one direct try has failed, or 4 seconds, it dials the inviter through those relays (`relayThrough`), and the inviter's daemon follows.
- **A join through the inviter's side.** While an invite is open the inviter asks up to two teammates to carry it with a key pair only the code gives, and publishes their relay keys for whoever holds the code.
  - From `prover` (see [Invites](#roster)), HKDF-SHA256 with the info strings `elu-code invite relay record`, `elu-code invite relay box` and `elu-code invite relay joiner` gives three 32-byte values: the seed of the key pair the record is published under, an AES-256-GCM key, and the seed of the key pair the joiner shows the relay.
  - The record is a HyperDHT mutable record: a 12-byte nonce, the 16-byte tag, then up to four 32-byte relay keys, sealed. DHT nodes that store it see its public key, the sealed bytes and the inviter's IP address. Without the code they cannot read it or tell which invite it is for. It is published again when the relays change and every 30 minutes, and replaced with an empty one when the invite is used or expires. Nothing is published while no teammate can carry.
  - The joiner reads the record, connects to those relays with the key pair from the code, and dials the inviter through them.
- **Direct or relayed.** `elu peers` and `state.json` say `relayed` for a connection whose stream is still on the relay socket it was paired on, and `direct` otherwise. A direct connection to the teammate that carries is `direct`, though its relay answers on the same address.
- **After the join.** Two machines that joined through a relay keep one. Each asks its own helpers to carry it with the other, by their real keys, tells the other with the notification `elu.route {relays}`, and saves both lists in `peer/routes.json` (mode 600): `{key: {mine: [{helper, relay}], theirs: [relay], told: [{helper, relay}]}}`. `elu.route` also carries `by`, the computer that runs each relay, in the same order; it is kept as `told`, so both sides can name it. Every later dial of that teammate names one of those relays, the next one each time, a direct connection is still tried each time, and HyperDHT moves a relayed one to a direct one when it can. A route is dropped when the two are no longer on a team. A relay named by a teammate is used for connections to that teammate only.
- **Two teammates.** Two computers on a team that cannot connect directly reach each other through a third computer on the team that reaches both. Nothing is set up: every daemon on a team carries for its own teammates.
  - A dial to a teammate that ends the way a blocked one does (their computer answered, the two could not connect) makes the daemon ask every teammate it reaches directly that is on a team with that one: `elu.carry {with: key, reach: true}`. With `reach` the computer asked makes a relay only while it reaches that key itself, directly, so both keys the relay lets in are its own teammates; otherwise it answers `{relay: null, online: false}`. Up to two relays are kept.
  - The route is kept as after a join, and the teammate is dialled through it at once. The other side follows the relay the dial names, keeps the route too, and asks its own helpers.
  - A daemon that admits a teammate it reaches directly tells it which other teammates on a team with it it also reaches directly, and tells each of those about it, with the notification `elu.reach {here: [key]}`. Each dials the other at once and looks for a way, rather than at its own next try, which after a long time apart is up to about 15 minutes away (Hyperswarm waits 10 minutes or more between tries to a computer that was gone a while). Only a daemon whose hello says `reach: 1` is told; an older one is not, and works as before.
  - While the two are not connected, the daemon dials and asks again every 15 seconds, and at once when a teammate connects. While a teammate on a team with that one is still connecting, or one did not answer in time, the way is still looked for: it asks again within 3 seconds, for up to a minute. Only once every one of them has answered or could not be reached, and none carries it, or 3 tries in a row through a relay failed, does the row say there is no way through, and only then do the tries come twice as far apart each time, up to 5 minutes. When the computer that carried goes away, the connection ends, the dial through its relay fails, and the next computer that reaches both is asked in the same way. That holds when it goes without a word, as when its lid is closed: the dial then ends with the relay's error (`CHANNEL_CLOSED`), which counts as blocked, because HyperDHT goes to a relay only after the teammate's computer has answered.
  - Back to direct: every dial through a relay tries the direct way as well, and HyperDHT moves the connection over when that works. While a connection stays relayed, the side with the smaller key tries a direct connection of its own every 5 minutes, then twice as long each time up to an hour. When one opens, it drops the relayed connection and dials again, which then goes direct; the teammate shows offline for about a second meanwhile.
  - The computer that carries sees what a relay of a join sees: both IP addresses, when the two are connected, and how much they send. It cannot read it, since the two ends run Noise between them. Its relay lets in the two keys it was made for and no one else, for 10 minutes unless asked again.
  - `state.json` gives each member `via`, the computer that carries (`li's computer`, `li's computer studio` when it has a box name, `a relay` for a relay of the team, else `another computer`), `reach: "looking"` while a computer on the team that reaches both is still looked for (and for a minute after a teammate said it reaches them), and `reach: "blocked"` for one that is not connected although their computer answered and no computer on the team got it through. `elu peers`, the Team list and the teammate's window say `online · through li's computer` for the first, never offline, `offline · looking for a way through` (`looking for a way through`, `looking for a way` where narrow) for the second, and `offline · no computer on the team reaches you both` for the third. Right after a join that went through a computer, the connection still runs on the relay the invite gave, which is in no kept route: the inviter knows which computer runs it and says so in `elu.route` (`now: {relay, helper}`), at once when the other side's `elu.route` does not say it, so both rows name it. A row too narrow for `online · through kim's computer` says `through kim's computer`, since its dot says online. A row too narrow for the reason says `offline · no computer reaches you both`, `offline · nobody reaches you both` or `offline · no way through`, the longest that fits, and the teammate's window says it whole. A teammate whose computer is off is plain `offline`.
- **No way through.** With no computer to carry it, or none that could, the join ends after the 3 minutes and says so, with what works: joining from another network, or while ELU is open on another computer on either one's team.

## Status

- Status is on by default when a project is shared; `elu share --no-status` turns it off. While it is on, `elu.status` carries one row for each live task that edits the project (preparing, running, ready or waiting for input), at most 50 rows in all: `{repoId, handle, taskId, label, now, files}`. A session that only answers has no row.
  - `label` is the first line of the task's request, up to 80 characters.
  - `now` is what the task is doing: its state and who is at work (a role such as `lead`, a shared bot's `@name`, or `bot` for a bot that is not shared), up to 80 characters.
  - `files` is up to 200 paths, relative to the project, of the files the task changed from the commit it started from, and of the new files Git does not ignore.
- The rows go only to connected teammates on a team the project is shared with, as its name does. A project with no `origin` remote has no `repoId` and sends no rows.
- Every 10 s the daemon builds the rows again and sends them when they changed.
- `repoId` is the sha256 of the normalised `origin` remote URL, so the same repository matches across machines.
- Overlap is computed locally: my live tasks' changed files against teammates' rows with the same repoId. No query is sent for it.
- Status is also sent on every connection, even with no rows, and a teammate's saved rows are shown only while they are connected.
- `elu.status` also carries `box`, the name of the machine, and `bots`, the bots its owner shares: `[{name, about}]`, at most 20. These two go to every connected teammate, also when no project is shared or status is off.
  - The box name is the peer setting `box`. With none set it is the first label of the host name, without any character a box name cannot have and cut to 32 characters, or `box` when nothing is left.
  - The owner sets it with `/computer name NAME` in the app or `elu id --computer NAME`, and clears it (back to the host name) with `/computer name default` or an empty name. A name that is not a box name, `here`, `model`, `everyone`, a bot's name (one ELU comes with, one saved on this computer, or one another computer on his teams shares; on his other computers `@name` finds the bot first), or the box name another computer on his teams last said it has (any case) is refused, and nothing is saved.
  - The daemon reads the box name and the bots file again on every tick. When either changes, every connected teammate gets a new `elu.status` on that tick.
  - The receiver checks each field on its own. A box name that is not valid reads as none. A bot with a bad name, or an `about` that is not text, is dropped. An `about` is cut to one line of 120 characters.
  - The daemon keeps what each teammate last said in `state.json`, so it is still known after a restart while they are offline.
  - A machine on an older build reads only `rows` and sends neither field. It shows with no box name and no bots.
- `elu.status` also carries `boards`, the repositories this machine shares with the teams the two machines are both on: `[{repoId, handle, commit, teams}]`, at most 20. It says which team boards a teammate's own clone of a repository is on ([Tasks](#tasks)). A machine on an older build sends none.
- `elu.status` also carries `repos`, one proof for each repository this machine has, for the Kanban ([Kanban](#kanban)). A machine on an older build sends none.
- `elu.status` also carries `projects`, each project this machine shares with a team the two machines are both on: `[{handle, name, repoId, address, teams, project?}]`, at most 20 ([Projects a teammate shares](#projects-a-teammate-shares)). `project` names the projects of those teams it is (the team's id for its first, `<team id>:<id>` for another, see [A shared project](#a-shared-project)); a computer that joined that project in a folder of its own has that folder as the project, so it does not list the teammate's as another one. A machine on an older build sends no `projects`, and one from before this build no `project`: its row shows as before.

## A shared project

An invite shares the project it was made in (`elu invite` the folder it runs in, `/invite` the open project), and a computer that joins with it (`/join` in a project, `elu join` in a folder) takes the folder it joined in as that project (never the home folder or above it). Each computer knows its own folder of each project of the team (`lib/peer/project-share.mjs`), whatever its folder, repository or name, and the projects stay apart: each has its own sessions, Tasks, instructions and memory.

- **The team's first project** is the one the first invite shared, and the folder each computer joined it in (`peer/access.json`, the team's `root`). Once anyone else is on the team, or the team has another project here, that folder is kept in `peer/team-roots.json`, and nothing moves it: `/access` in another folder moves only where teammates' messages run. A computer that joined only another project of the team has no first project: a folder it shares or sets with `/access` later never becomes one. A computer that kept none (a team nobody joined yet, or one from before ELU 0.1.30) takes the team's `root`, else the share in `team-projects.json`. On the wire it is the team's id, as from ELU 0.1.29 on.
- **A computer whose join set no folder** (ELU 0.1.19 set none, and a join in the home folder sets none), or whose folder is no project here any more, is on the team all the same (0.1.31 on, `onlyProject` in `lib/peer/project-share.mjs`). With one project, that one is the team's first project here: kept in `team-roots.json` once the join is a minute old, so the folder a join names wins and a project added later never moves it. Only once a teammate told this computer of the team's first project (`project` naming the team in `peer/shared/<key>.json`): on a team nobody shared a project with (an invite made in the home folder shares none) the one project here stays its own, and nothing of it reaches the team. Never one that is another team's project here, never on the computer that made the team, and never on one that joined only another project of the team. With several projects none is taken: Projects shows the team's project by its name with "no folder here yet" and every computer's sessions of it. Enter opens its page: Sessions (every computer's sessions of it, under each computer), Kanban (its board: those sessions as cards, and its Tasks where it has a repository), Instructions and Memory (to read, as the team's computers sent them: a computer that says it has no folder of the team's first project is sent that project's instructions and memory in `elu.notes`, as its sessions reach it) and Folder here. The first new session in it, Folder here, or e on its Instructions or Memory asks "Which folder here is ELU?", the open project first; the one chosen is kept the same way, and its instructions and memory come into that folder. A folder the join named that is no project here (never opened in ELU, or gone) is no answer: the folder chosen takes its place in `team-roots.json`. A teammate's project is never matched by its repository alone.
- **The name** a team's first project goes by on a computer that did not make the team is the name the founder's computer gives it (`peer/shared/<founder>.json`), unless the folder was given a name of its own here; the name a new project gets, its folder's, gives way to it. There is no "shared by" row for a team this computer is on.
- **Another project of the team.** `/share`, `elu share` or an invite in another folder shares that folder as another project of the team, under an id of its own (16 hex characters, made at random by the computer that shared it first): `peer/team-folders.json`, `{<team id>: [{id, root}]}`. An invite made there carries the id (`project` in its row of `invites.json` and in the reply to `elu.invite.prove`), and the computer that joins with it keeps its folder under that id, before what teammates can do there is saved, so it is never taken for the team's first project. On the wire such a project is `<team id>:<id>` wherever a team's id names a project (`teams` in `elu.remote.list` and `elu.notes`, `project` in `elu.status.projects`). An ELU up to 0.1.30 reads only a team's id there, so it never takes another project for its first, and a code for another project tells it, before it is let in, "This invite is for another project of the team. Update ELU, then join again: npx -y @elu-labs/elu@latest" (its hello has no `projects: 1`); the code stays unused. A code made in the first project names none, and joins any ELU as before.
- **An invite shares its project with status on.** `/invite` and `elu invite` share the folder they are made in with status on, so a project kept off with `/share off` is shared again, and the code names it whether it was kept off or not.
- **Someone already on the team** who uses a short code (ELU 0.1.31 on, hello `projects: 1`) is not admitted again: the inviter marks the code used and replies `{teamId, inviter, ops, project?, member: true}`, and the folder it was used in becomes the project the code was made in (the team's first when it names none and that computer has no first yet). What teammates can do there stays as it was. An older ELU is told "You are already on this team.", as before.
- **Who is told what.** A teammate's computer is told the sessions and sent the instructions and memory of the projects of a team that it has a folder of, never another project of the team. It says which (0.1.31 on): `slots` in `elu.remote.list`, the projects of the teams both are on it has, kept off or not; and the projects with their `teams` in `elu.notes`, which go with their notes only once the other has said it has that project too (until then with `notes: null`, which every build reads as nothing to take). For a team it says no project of (an older ELU says none), it is told the team's first project, as before.
- **A message names the project it was written in.** A message written in another project of a team, naming no project, carries `slot: "<team id>:<id>"` in its peer metadata; the receiver runs it in its folder of that project, not in the folder `/access` sets for the team, with that team's rules; there it waits for the owner, as a message that names a project does, unless `/access` set that folder. An older ELU drops the field and runs it where it ran before.
- A refusal that ends a join still reaches the joiner: the inviter ends the connection only once that answer is out (at most 2 seconds), so an ELU before 0.1.31 reads why it cannot join, not that the teammate went away.
- A share with status off, or a project kept off with `/share off`, is no team's project.
- **What ELU 0.1.29 mixed.** 0.1.29 made the project shared last the team's project, so a `/share` or invite in another folder had that folder trade instructions and memory with the teammates' folders of the first one, which passed them on to the first one once 0.1.30 put it back. Once, on the first trade after an update (`lib/peer/put-back.mjs`, `peer/notes/put-back.json`), each computer looks for two of its projects that did that: a folder shared with a team that is not its first project, which traded with a teammate's computer it is not shared with now, as the first one did. Only a computer that was never the owner's counts: no mark either way in `peer/mine.json`, still on the team, and its notes last came as a teammate's (`theirs` in `peer/notes/from/<key>.json`). One of his traded every project before 0.1.29, so one that is not his any more says nothing. A lesson that a session of one of them saved ("Saved to project context") and no session of the other did goes back: it is taken out of the other, or kept out of it when it is not there yet but another computer's copy of that project still has it, there and on the teammates' computers, as any lesson the owner takes out is, and the app says so once ("A lesson of Team notes that ELU 0.1.29 put in ELU was taken out."). Nothing else is taken out, since it cannot be told apart for sure: when such a project still has a lesson no session here saved, or the same instructions or text as the other, one line at the end of the owner's text in its context says so: "ELU 0.1.29 mixed this project with Team notes. Lessons learned in a session were put back where they belong; check the rest, and the instructions, for anything that belongs to Team notes."

- `hello` carries `shared: 1`. A computer sees the sessions of a teammate's computer whose hello says `shared: 1` and that is on a team with it, as it sees those of a computer of its owner's: it asks `elu.remote.list` every few seconds, `elu.remote.watch` and `elu.remote.since` for the one its owner opens, `elu.remote.older` to page up, and `elu.remote.check` with `look` for its Task. The host answers these to any key on a team with it: a key that is not its owner's is told only the projects of a team both are on that it has too (see [A shared project](#a-shared-project), "Who is told what"), with their sessions, and its top agents not at all. The list says which of those teams each project is (`projects[].teams`); when the projects a key may see change, the next list is `full`. A watch, catch-up or page of any other project's session reads "That session is not on this computer." The host's events go to that key for those sessions alone. An archived session is its computer's own: it is never listed or sent to that key, even when it asks with `archived: true`.
- Every other method (`start`, `send`, `files`, `stop`, `answer`, `task`, `rename`, `archive`, `delete`, `check` with an answer, `board`, `boardAct`, `folders`, the standup ones) still needs a key that is the owner's on both sides, as before. The viewer does not ask them of a teammate's computer: a key or a command such as `/send` on such a session says at once "It is sara's session: only sara can work in it.", and asks nothing. A request that gets there anyway is refused: "Only the owner of @studio can do this there."
- The viewer keeps that computer's list as for one of its owner's, with `theirs: true` (`peer/remote/machines/<key>.json`). Sessions shows its sessions under "On studio · sara", the computer's name and its owner's, the sessions of the open project when that is the same team's project here, else under the project's name there. A row there opens (Enter) and shows its changes (d); its key bar offers nothing else, the message box reads "sara's session on @studio · read here", and what is typed there goes nowhere: "It is sara's session: only sara can write to it." Its Task, when it waits, "waits for sara's approval", with no y or n. Projects counts its sessions in the project here that is the same team's project. In a project kept off here with `/share off`, no teammate's session shows, in the list or in its counts.
- The project's instructions and memory are put together with that computer's (Instructions and memory above), for that project alone.
- A computer up to ELU 0.1.28 says no `shared` and is neither asked nor sent any of this: it shows what it showed.

## Projects a teammate shares

A project shared with a team is a row in the Projects tab of every member of that team whose computer does not have it: its name, who shares it and the machine it is on. A project of a computer that is not shared with a team this computer is on is not listed, whoever owns that computer. A share keeps its row.

- **What is sent.** In `elu.status.projects`, for each project shared with a team the two machines are both on (also one shared with `--no-status`, but not one turned off with `/share off`): its share `handle`, its `name` (the project's name, at most 60 characters), its `repoId` (null with no `origin` remote), the `teams` it is shared with that both machines are on, and `address`, its `origin` remote when a teammate could clone it: an https, http, ssh or git URL, or `user@host:path`. A folder of this machine, a `file://` URL and anything else are sent as null. A password or a token in the remote is never sent: an https address goes without any user, an ssh one keeps its user (`git@`) only. The list is sent on connect and again within a tick when a project is shared, unshared, turned off or on, or renamed.
- **Receiving.** Every field is checked and unknown ones are dropped. An address is kept only when it is one of the forms above and names the repository `repoId` says, so the address of one repository cannot stand in for another. The list is kept in `peer/shared/<key>.json` (mode 0600), replaced by each `elu.status`, and deleted when its sender is no longer on a team with this machine.
- **One row for one project.** Shares of the same repository (the same `repoId`) are one row that names everyone who shares it, online first. A registered project of this computer with that `repoId` is the row: the project is never listed twice. Unsharing, `/share off`, the sharer leaving or being removed, or this machine leaving the team takes the row away.
- **Its team board.** Enter opens the project in Kanban, read-only: the Tasks ([Tasks](#tasks)) and the session cards ([Kanban](#kanban)) its team told for that repository. A session card of a project shared with a team also goes to the members of that team who have no clone, so no proof, when the session works in the shared project's own repository; `/share off` and unsharing stop it. Such a card is kept only from a teammate whose `elu.status.projects` names that repository for a team both are on.
- **Writing to whoever shares it.** The message box on that board sends an ordinary question to the teammate who shares the project, with `metadata.project` set to its handle. It starts a session in that project on their computer, or waits for them, as they chose under [What teammates can do here](#what-teammates-can-do-here).
- **Bringing it here.** `c` on the row asks for a folder (`~/<handle>` is offered) and runs `git clone` of the address into it, with no prompt for a password (a private repository needs your own git sign-in on this computer). The clone is registered under the project's name and becomes the active project. With no address there is nothing to clone, and the line says to copy its folder here and run ELU in it.
- **A teammate on 0.1.19** sends no `projects`. Their rows are built from the repositories in their `elu.status.boards` and the share handles their `elu.hello` named: the handle is the name, and there is no address, so `c` on a project that has a repository says that their computer needs 0.1.20. The hello of the connection a machine joined their team through came before it was a teammate and names nothing, so after such a join the machine closes that connection once (the first time their `elu.status` arrives without `projects`); the two connect again at once, and the new hello names what they share.

## Kanban

Anything anyone works on in a repository shows on one Kanban for everyone on the team who has that repository. No `/share` is needed. Every computer counts the same here, whoever owns it.

- **Which board.** A session is on the board of the repository it works in, from its first message: the one its edit runs in; else the one its proposed or approved Task names for the edit; else the project, when it is a clone; else the clone the session's folder is in. A session with none of these (a conversation in a parent folder, one that asks you first, one whose Task waits for you) works in the project's main repository: the one clone in the project's folder, or with several the repository of the project's most recent session that has one, else the clone whose folder has the project folder's name (in any letter case). Two clones are the same repository when their `origin` remotes match (the same `repoId`) and they have the same first commit. A project whose folder is above its repositories (a parent folder, or your home folder) has one board for each repository its sessions work in, and for each repository in its folder that a teammate's sessions work in. The header's `Board` button picks one. The board of the session you last opened in the project comes first. A session that works in no repository shows on each of the project's boards, as a card in To do does, and is not sent to teammates. A session is one card on your board while its first turn runs.
- **What a teammate sees.** Each of your sessions as a card in the column your own board has it in: In progress while it works, Needs you when it waits for you, Done when it is finished. Beside the title: `@name` of who started it (you, or the teammate whose message started it) and the name of the machine it runs on. Enter opens it to read, as it opens one of your own cards: its whole Task when its machine told it (where it stands, its priority and severity, who started it and where, the goal, the description, the objectives with the met ones marked, the success criteria, the subtasks and the ETA), else `No Task yet`, and when it last moved. Nothing on another machine can change it.
- **What is sent.** For each session, only `{repoId, id, title, column, by, at}`, plus `plan`, the id of its Task when it has one (so a Task card and its session card show as one card), and `remote`, its id on the computer that started it, sent only to that computer, `standup`, whether a standup would ask it ("Standup" below). `own`, `ref`, `task` and `first`, which ELU 0.1.26 to 0.1.33 sent to the owner's other computers, go to no computer, and are dropped on the way in from one that still sends them. The oldest cards are left out while the message would pass 960 KiB, so it fits in one frame. `title` is the session's name or the first line of what was asked, at most 80 characters: every absolute or `~/` path in it reads `[path]`, and a title with a secret in it is sent as `Session`. `by` is at most 40 characters. `id` is a hash of the session's number and folder with a random secret this machine keeps in `peer/card-secret` (mode 0600), so it stays the same here and tells no one else either. Never the chat, a file, a diff or a path.
- **Who asked stays in the team it came through.** A session a teammate's message started has their words as its title and their name as `by`. Its card goes as it is only to that teammate and to teammates on a team the message came through (the teams of the project it runs in, else every team that teammate shares with this machine). Anyone else gets it with the title `Session` and `by` `teammate`.
- **Proof of a repository.** Each machine sends each teammate, in `elu.status`, one proof for each repository it has: the sha256 of the two machines' keys, the `repoId` and the repository's first commit. Only someone with a clone of that repository can make the matching proof, and it is good for those two machines only. A card goes only to a teammate whose proof matches this clone, and is kept only from one whose proof matches the receiver's. A repository the other side does not have is never sent, and a clone with another first commit gets no card. At most 200 proofs.
- **Which repositories a machine has.** Every project that is not kept off: the project itself when it is a clone, else the clones in its folder (hidden folders, dependencies and editing workspaces are skipped; at most 60, looked for again every 10 minutes), and the repositories its sessions of the last two weeks work in. Never the home folder, or a folder above it, as a repository. The daemon looks every 30 s, and at once when a project is opened, so teammates' cards show on its Kanban, and a standup asks them, within seconds of opening it.
- **What the board keeps.** Archived sessions are not sent. A session you moved to Done is sent as Done. As on your own board, a session quiet for 14 days leaves unless it is in progress or done, and every finished session of each repository is sent.
- **Keeping one project off.** `/share off` in a project keeps it off both ways: its sessions are told to nobody, its repositories are proven to nobody, and teammates' sessions are not shown in it. A project shared from here with status off is kept off too. `/share on` puts it back.
- **When.** `elu.cards` carries the whole present list for that teammate, on connect and within 5 s of a change, so a session that ends or leaves is absent from the next list. Every card goes, each with what it carries: a list too long for one message goes in parts, as a long list of Tasks does ([Tasks](#tasks), "Size"). Only a machine whose `elu.hello` says `cards: 1` is sent any.
- **Receiving.** Every field is checked: control characters, terminal escapes and invisible characters are removed, white space becomes one space, text is cut to its limit, unknown fields are dropped, and a card that fails a check is dropped. The list is kept in `peer/cards/<key>.json` and the proofs in `peer/board-repos/<key>.json` (mode 0600). Every one of a teammate's cards is shown on its board. An offline teammate's cards stay, marked offline, for 48 hours after they were last connected, and are deleted at once when they are no longer on a team with this machine.

## Standup

`/standup` ([Standup](standup.md)) asks open sessions on other computers too. Only a machine whose
`elu.hello` says `standup: 1` is sent any of this; an older one is listed in the Standup as
not asked, and shows an asked session's rows as plain chat.

- **A computer on a shared project.** The remote listing marks a session the host would not ask with `standup: false` (moved to Done, quiet for a week, a Standup, no agent), and the asker leaves those out before it counts. `elu.remote.standup {round, refs, question?}` names sessions by the refs of the remote listing. The host asks each one only if it would ask it itself (open, with an agent, not a teammate's question) and that project is Auto for that computer there (else it is skipped: "Its project takes work by hand here."), in the same read-only answer turn, and answers `{asked: [{ref, title}], skipped: [{ref, why}], records: [{ref, record}]}`, or `{older: true}` while its conductor still runs an older build that would take the question for a plain message. `record` is what the host has on record for that session, read with no model run (`lib/standup-record.mjs`): `{state: working | waiting | finished | blocked | stopped, since?, question?, reason?, detail?, task?: {title, state, done, of, now?}, said?, command?, file?, step?, pr?, branch?, at?, who?}`; the asker keeps only those fields and shows them at once. A host on ELU 0.1.19 or earlier sends no `records`, and the asker's Standup says so in that session's block. A session in the middle of a turn is answered beside that turn, at once, with no slot taken. `elu.remote.standupRead {round, parts?, refs?, from?}` gives `{answers: [{ref, title, who, text, at, failed?, from?, more?}], pending: [{ref, working, queued, why}]}` (`why`: `queued`, not started yet; `writing`, its run goes; `older`, the conductor there is from before its update and answers when the session's turn ends), and `elu.remote.standupStop {round, refs?}` takes back the questions not started and stops an answer run that goes, the one beside a turn too, without touching that turn. A round is kept a day in `peer/remote/standup/`.
- **A teammate's computer.** A session card carries `standup: true` or `false`, whether a standup would ask it (the same rule as the owner's own sessions: not moved to Done, with an agent, active in the last week, working or waiting); a card of an older build carries neither, and one of those in Done is not asked but listed in the Standup, since it may have answered. A session a teammate's message started is never asked, its card withheld or not: the answer skips it with the reason `your message started it` to that teammate and `a teammate's message started it` to anyone else. `elu.standup.ask {round, cards, question?}` names sessions by their card ids on the shared Kanban: only cards this machine tells that teammate, of the owner's own open sessions, every one named. It counts toward the teammate's 200 messages a day; a muted teammate is declined. A round is one of the teammate's requests for the day. What a session has on record costs nothing; each model update holds $0.10 of the teammate's daily allowance and their teams' while it runs and then counts what its turn cost ($0.10 when its vendor reports no cost), so with the default caps a round of 26 sessions gets all 26 updates. A session past a limit is not asked, and its answer says which limit in plain words, such as "Not asked: you have used the $5.00 a day this teammate's computer allows you."; the owner's chat of that session says the same of the teammate. The approval is checked again when the owner says y: a teammate no longer in a shared team, or muted, is declined. While the conductor there runs an older build, the answer is `{older: true}` and nothing is asked. When every team the two share is set to Auto, the sessions are asked at once; otherwise the owner sees one item for the round, where y asks and n declines. The answer is `{state: asked | waiting | declined, asked: [{card, title}], skipped: [{card, why}]}`. `elu.standup.read {round}` gives `{state, answers: [{card, title, who, text, failed?, held?}], pending: [{card, working, queued}]}`, and `elu.standup.stop {round, cards?}` stops it. A round is kept a day in `peer/standup/`; asked again, it is answered as before, so each session answers at most once a round.
- **Updates go back whole.** Neither side cuts an update. An asker on this build says `parts: 1`, names the sessions it still waits for (`refs`, or `cards` for a teammate), and gets up to about 500 KB of updates in one answer, so every answer fits one line on the link; the rest come with its next read. An update longer than that comes in parts: `more` is the character the next part starts at, the asker asks again with `from: {<ref or card>: <character>}`, joins the parts, and takes the update once its last part is in. `elu.standup.read` works the same way. An asker on ELU 0.1.19 or earlier says none of this and cuts each update at 4,000 characters itself; it is sent no more than that.
- **What a teammate's answer turn gets and gives.** The question inside a peer-data block, the owner's rules for those teams, and the read-only answer instructions. What goes back is checked as any answer to a teammate is: paths are cut (an absolute or `~` path, and a relative one that leads out of the project, such as `../notes/x.md` or a folder the project does not have, become `[path]`; `src/coupon.mjs` in the project goes as written), and an update that may hold a secret is replaced by "Its update was held back: it may hold a secret." Only the update, the card's title and the agent's name leave the machine. The asker checks every field again, and its Standup model reads a teammate's update only inside a peer-data block.

## Tasks

A Task is a session's approved plan: what the owner agreed the model should do. A team has one board for each repository a member shared with it. Every member's project of that repository is on it, whether that member shared it or not: their machine tells the team which Tasks its sessions there are working on, and shows the others' Tasks on its own Kanban.

- **Same repository, same board.** A project is on a team's board when this machine shares it with that team (`/share`, `elu share`, or the invite that shared it), or, when this machine does not share it, when its `origin` remote is the same repository (the same `repoId`) as a project a member of that team shares with it and this clone has the first commit that member names. The second needs nothing on this machine: a teammate who joins and opens their own clone is on the board without sharing it, and is never asked. A project shared from here is on the boards of the teams it is shared with and no others: a teammate's claim never adds a team the owner did not choose. Never for the home folder or a folder that holds it, never for a project with no `origin` remote, never for a clone without that first commit (a shallow clone may lack it), and never for a project kept off (below).
- **How a machine learns which repositories are on the board.** `elu.status` carries `boards: [{repoId, handle, commit, teams}]`: each project the sender shares with a team the two machines are both on (status on or off), with those teams. `commit` is the repository's first commit (`git rev-list --max-parents=0 HEAD`, the oldest when there are several); a project with no commit yet is not listed, and a row without a valid `commit` is dropped. The receiver checks it with `git cat-file -e <commit>^{commit}` in its own clone, so naming a repository's remote is not enough to bring someone's clone of it onto a board; for a public repository the first commit is public too. At most 20. The receiver keeps the last list from each teammate in `peer/boards/<key>.json` (0600) and replaces it with the next; a claim counts only for a team both machines are active members of. The sender sends a new `elu.status` within a tick of a share, an unshare or a team change. A teammate who is no longer on any team with this machine has their list deleted.
- **Keeping one project off.** `/share off` in a project keeps it off every board both ways: its Tasks are told to nobody, whatever a teammate shares, and teammates' Tasks are neither shown in it nor given to its models. For a project shared from here it also switches its status off. `/share on`, or `/share` again, puts it back. The list is `peer/board-off.json`. `elu unshare` says when someone else's share of the same repository still keeps the project's Tasks on a board.

- **What is told.** For each session of the project, the Task whose work is going on (its newest approved one), and any Task finished within the last 24 hours. Each is `{repoId, handle, id, revision, title, description, goal, objectives, priority, severity, state (approved or done), startedBy (owner, schedule or handoff), who, subtasks: [{text, state}], met, approvedAt, doneAt, updatedAt, criteria, estimateMinutes, etaMinutes, etaAt}`. `criteria` are the success criteria (at most 8, 200 characters each); `estimateMinutes` the model's estimate of the work from approval to done, and `etaMinutes` its last revision of the minutes left, made at `etaAt`. An older build sends none of the last four, and its Task reads as not set; an older build drops them on the way in. `who` is the model's name, a shared bot's `@name`, or `bot` for a bot that is not shared.
- **What is never told.** A Task that is only proposed or was rejected, the request and repository that approval starts, the chat, file contents, and any path of the machine. While status is on, a [status row](#status) does carry the first line of that request and the changed paths inside the project.
- **To whom.** A teammate on a team whose board the project is on. Also, with no `/share`, every session's Task goes where its card goes ("Kanban" above): to each teammate on a team with this machine who proved they have the session's repository, the one the card names, and one a teammate's message started only to that teammate and the teams it came through. The receiver shows it only in its project of that repository, and only from a teammate whose proof matches its own clone. A project shared from here with `status: false` tells nothing, and neither does a project with no `origin` remote, since it has no `repoId`, or a project kept off.
- **When.** `elu.plans` carries the whole present list for that teammate. It is sent on connect, and within 5 s of a change (so at most one every 5 s to each teammate, well inside the 20 requests in 10 s a connection allows): an approval, a subtask's state, a finished Task, a new revision, a repository newly on a board. A Task that ended, or whose project left the board, is absent from the next list, and the receiver replaces what it had.
- **Size.** Every Task goes: ELU sets no limit of its own on how many. A list that fits one message (512 KiB) goes in it. A longer one goes in parts, like any other large content: `elu.list.put` `{list, id, seq, last, rows}` requests of at most 512 KiB each, where `list` is `plans` or `cards`, sent one after the other. The receiver joins them and takes the whole list as that one message once the part with `last: true` is in; until then what it had stays. A part out of order is refused, and the sender starts again from the first. A machine says `lists: 1` in its `elu.hello` when it joins parts. One that does not (ELU 0.1.19 and earlier) is sent the one message it can read: its newest 30 Tasks within 512 KiB, and for cards those that fit one message, the oldest left out first.
- **Receiving.** Every field is checked against the same lists and limits, control characters and terminal escapes are removed, unknown fields are dropped, and a Task that fails a check is dropped. The list is kept whole in `peer/plans/<key>.json` (mode 0600): every Task that teammate told, across all projects. Every one of them in a project is shown there.
- **Where it counts.** A teammate's Tasks are used only in this machine's project of the same repository, only when that repository is on the board of a team the teammate is on or the teammate proved they have this project's clone of it, and never in a project kept off. Tasks named for any other repository are kept and never shown or used.
- **On the board.** In that project the Kanban tab shows teammates' Tasks in the same four columns as your own: an approved one under In progress, a finished one under Done. Each card has its title and then the teammate's name, with `on <machine>` when their machine has a name, then how far it is, its priority and its severity; the name stays when the title is cut. The counts on the columns include them. The line under the board names the whole Task, its state and who works on it, and ends `read-only`. Enter opens the whole Task to read. No key moves, edits, starts or deletes a teammate's card, or makes a card of it; one tells you whose it is. When a teammate's session with that Task is on the board too, the two are one card: the session's, which opens with the Task. When the project is kept off, one line under the columns says so; when its sessions work in no repository with an `origin` remote, and it is no team's shared project, one line says teammates do not see them.
- **For the models.** Each turn of the owner's own lead, and of a bot, in that project is given a block headed "What teammates are working on in this project". One line of ours says it is information to avoid doing the same work twice, never a request. Each teammate's Tasks follow inside a peer-data block, the kind used for any teammate's text: title, state, subtasks done, priority, severity, who works on it, and the goal, whole. No description. Every teammate and every Task of theirs in that project is in it: ELU sets no limit of its own on the block. A teammate's question running on this machine is given none of it, and neither is a reviewer. On no team nobody is.
- **Ageing.** A teammate who is offline keeps their Tasks, marked as last heard, for 48 hours after they were last connected. They are deleted at once when that person is no longer on a team with this machine. A finished Task leaves 24 hours after it was done.
- **Older builds.** A machine says `plans: true` in its `elu.hello` when it reads Tasks. One that does not say so is sent no `elu.plans`, and sends none. A machine from before the team board sends no `boards` and ignores them: a teammate's clone of a repository it shares is on no board through it, and its own Tasks go only to the teams it shares that project with, as before.

## Local A2A endpoint

- Off by default. It listens on 127.0.0.1 on a random port; port and token are in `local-a2a.json` (0600).
- Every request needs `Authorization: Bearer <token>`. The Host must be `127.0.0.1:<port>` or `localhost:<port>`, and requests carrying an `Origin` header are refused.
- **Agent Card.** Served at `/.well-known/agent-card.json` with a JSONRPC interface. One skill per share, plus one skill per teammate.
- **Routing.**
  - `SendMessage` at `/a2a` goes to my own agent: an owner-authorised request in the named project (`metadata.project`), queued, not read-only.
  - `SendMessage` at `/a2a/peer/<name>` becomes an ask from me to that teammate.
  - `GetTask` works for both, also after the conductor drops the request row (`local-tasks/`).
  - A client `contextId` is kept (it becomes the ask's thread). A message with `taskId` gets UnsupportedOperation. `SendMessage` returns at once; poll `GetTask`.
- **Conformance.** Tested with the official `@a2a-js/sdk` 1.3.0 client (a dev dependency).
